## 一、怎么突破的（三个改动叠加）

| # | 改动 | 效果 |
|---|---|---|
| 1 | **转换器流式写盘** | 峰值内存 5.65 GB → **362 MB**（不再 OOM）|
| 2 | **quantize_q4_0 向量化** | **提速 354×**（25.6 小时 → 3.25 分钟）|
| 3 | （前置）`tg_encode` 重写 + 特殊标记表 | 分词与训练一致（0/11 不一致）|

### 改动 2 的细节（关键）
```python
# 原实现：每个字节调一次 .item()
for j in range(0, QK, 2):
    low = q[j].item() & 0x0F
    high = q[j+1].item() & 0x0F
    out.append((high << 4) | low)
# V2.7 共 3.03G 权重 ÷ 32 × 16 = 15.2 亿次 .item() ⇒ 实测 25.6 小时
```

**向量化**（一次性 reshape 成 `[blocks, 32]`，全 numpy 运算）：
```python
wb = w.numpy().reshape(blocks, 32)
max_abs = np.abs(wb).max(axis=1)
scale = np.where(max_abs > 0, max_abs / 7.0, 1.0).astype(np.float32)
q = np.rint(wb / scale[:, None]).clip(-8, 7).astype(np.int8) + 8
qq = q.astype(np.uint8).reshape(blocks, 16, 2)
packed = (qq[:, :, 0] | (qq[:, :, 1] << 4)).astype(np.uint8)
```

## 四、⚠️ 待解决问题：生成只出 `<EOS>`

### 现象
```
prompt: <用户>\n你好\n<TGAI><回答>   (token: 32770, 8, 911, 2002, 8, 32771, 32773)
生成:   [3, 3, 3, 3, 3, ...]  ← 20 个 token 全是 EOS(3)
```

### 与 llama.cpp 侧的一致性
llama.cpp 那边也观察到类似现象。**已知的事实**（我在 GGUF 侧实测过）：
```
模板末尾只到 <TGAI> 时 → llama-cli 生成 0 token
原因：该 ckpt 在首位的原始首选是 EOG（停止符）
⇒ 模板必须【强制注入档位标记】（<回答> 或 <思考>）
```
**我已经注入了 `<回答>`**，但 TGAI GO 仍出 EOS。

### 可能原因（待排查，按可能性排序）

| # | 假设 | 验证方法 |
|---|---|---|
| **1** | **Q4_0 量化损伤** —— V2.7 是 BF16 原生，Q4 可能太重 | 转一份 **BF16 版**（5.64 GB）对比；BF16 对 BF16 源零损失 |
| **2** | 权重布局/转置与训练不一致 | 用同一批 token 对比 PyTorch 引擎的输出（云端 inference.py）|
| **3** | MoE 路由（QB 偏置）方向反了 | 对比"加偏置" vs "不加" vs "减偏置" 的输出差异 |
| **4** | RoPE / 注意力实现细节差异 | 逐层 dump 与 PyTorch 对比 |
| **5** | 特殊标记的 embedding 未正确读出 | 检查 32770-32778 行的 embedding 是否非零 |

### ★ 最该先试的（成本最低、可能性最高）
**转一份 BF16 版**：
```bash
python tools\tgai_convert.py \
  --checkpoint "D:\tgai_nlp\checkpoints\TGAI NB\TGAI NB 2.7\last_step.pt" \
  --output "D:\tgai_gguf_work\v27_bf16.TG" \
  --tokenizer "D:\tgai_nlp\checkpoints\TGAI NB\TGAI NB 2.7\tokenizer_v3tok.json" \
  --dtype bf16 --arch tgai_moe
```
- 输出 5.64 GB（磁盘够：D 盘 69 GB）
- **零精度损失**（BF16 源 → BF16 输出，逐位无损 —— 已在 C 的验收里证明）
- 转换也是流式 + 向量化 ⇒ 几分钟
- 若 BF16 版能正常生成 ⇒ 证实是 Q4_0 量化损伤
