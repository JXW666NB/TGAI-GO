# ★ 核显「反向传播 / 训练」可行性评估

**日期**：2026-10-10
**问题**：要不要做反向传播？用核显训练模型什么效果？
**结论**：**能做（显存够），但不值得做（带宽是死穴）。建议训练走云端。**

---

## 一、三条硬约束的实测结果

### ① 显存预算 ✅ 通过

训练显存 = 权重 + 梯度 + 优化器状态 + 激活。Adam + 混合精度的经验公式：

```
权重(BF16)      2 B/参数
梯度(BF16)      2 B/参数
优化器状态      8 B/参数   (Adam 一阶/二阶动量，FP32)
主权重(FP32)    4 B/参数   (混合精度需要)
------------------------------------
静态合计       16 B/参数
激活(检查点后)  约 2~6 B/参数   随 batch×seq 线性增长
```

| 参数量 | 静态 | +激活(典型) | 核显 7.25 GB |
|---|---|---|---|
| 10M | 0.15 GB | 0.20 GB | ✅ |
| 30M | 0.45 GB | 0.61 GB | ✅ |
| 50M | 0.75 GB | 1.02 GB | ✅ |
| **100M** | 1.49 GB | 2.05 GB | ✅ |
| 500M | 7.45 GB | 10.24 GB | ❌ |
| 1B | 14.90 GB | 20.49 GB | ❌ |

**⇒ 训练规模上限约 100M 参数**（比推理的 1B 上限小一个数量级，因为训练要多存 4 份状态）

### ② 原子浮点扩展 ✅ 通过（意外的好消息）

```
AMD Radeon 核显的设备扩展:
  ✅ VK_EXT_shader_atomic_float      ← ★ 反向传播梯度累加的关键
  ✅ VK_KHR_shader_float16_int8
  ✅ VK_KHR_16bit_storage
  ✅ VK_KHR_8bit_storage
  ✅ VK_EXT_subgroup_size_control
  ❌ VK_EXT_shader_atomic_float2
  ❌ VK_KHR_cooperative_matrix       ← 没有矩阵加速单元
  ❌ VK_NV_cooperative_matrix
```

**这意味着**：反向传播最麻烦的"梯度累加"可以原生做（`atomicAdd` on float），
不用走我之前用的"分段输出 + CPU 规约"绕路。
**⇒ 从"能做"角度，反向传播是可行的。**

### ③ 算力 vs 带宽 🔴 **这是死穴**

| 测试 | 吞吐 | 说明 |
|---|---|---|
| **纯计算（寄存器 FMA）** | **370.7 GFLOP/s** | ★ 核显算力上限（1M 元素 × 20000 FMA）|
| BF16 矩阵乘 seq=8 | 164.1 GFLOP/s | 计算/访存平衡 |
| **BF16 矩阵乘 seq=1** | **14.2 GFLOP/s** | **仅峰值的 3.8% —— 卡在带宽** |
| CPU AVX2 单线程 | 2.8 GFLOP/s | 参照 |

**诊断**：
```
核显算力不弱（370 GFLOP/s 对 15W 核显算不错）
但访问全局内存只有 ~7 GB/s 有效带宽
⇒ 矩阵乘（读权重为主）被打到峰值的 3.8%
```

## 二、训练成本推算（基于实测数据）

### 2.1 单步成本（50M 参数 MoE，seq=512）

```
权重总量: 50M × 2 字节 = 100 MB (BF16)

前向:  每 token 读一遍全部权重 = 100 MB
反向:  再读一遍（算梯度）      = 100 MB
       还要读写梯度+GradWeight ⇒ 又一遍 ≈ 100 MB
       --------------------------------
       每 token 内存流量 ≈ 300 MB

@ 7 GB/s 有效带宽  ⇒  每 token 43 ms
seq=512 一步       ⇒  512 × 43 ms ≈ 22 秒/步
```

### 2.2 完整训练需要多久

| 数据量 | 步数（bs=8, seq=512）| 时间（22 s/步）|
|---|---|---|
| 100M token | 24,414 | **6.2 天** |
| 500M token | 122,070 | **31 天** |
| 1B token | 244,141 | **62 天** |

**⇒ 训 1B token 要两个月。这个投入产出比不成立。**

### 2.3 对比：你有更好的选择

| 途径 | 相对速度 |
|---|---|
| **魔搭 MI300X（你已在用）** | **约 1000× 快于核显** |
| Featurize 4090 | 约 200~400× |
| 本机 CPU（AVX2 多线程，8.6 GB/s）| **约 1.2× 快于核显** |

**⚠️ 注意最后一行**：本机 CPU 的内存带宽实测 **8.6 GB/s（4 线程）**，
**比核显的 ~7 GB/s 还快**。而训练是带宽受限的 ⇒ **CPU 训练可能比核显还快**。

## 三、我的建议：**不做生产训练，但值得做一个小实验**

### ❌ 不建议做

1. **生产级训练** —— 根本原因：核显带宽 7 GB/s vs 云端 GPU 的 2000+ GB/s，差 300 倍
2. **在核显上训 1B** —— 显存就不够（需 20 GB，只有 7.25 GB）
3. **指望核显训出可用模型** —— 两个月换一个 50M 模型，不划算

### ✅ 值得做（如果目的是"玩波大的"探索）

| 项目 | 说明 | 工作量 |
|---|---|---|
| **反向传播内核** | 实现 BF16 矩阵乘的反向（dX / dW）+ Adam 更新 | 3~5 天 |
| **极小规模验证** | 10M MoE + 玩具语料（如字符级），验证训练管线闭环 | 1~2 天 |
| **对照实验** | 同一模型，核显 vs CPU vs 云端，量化加速比 | 1 天 |

**这样的价值在于**：
- 证明 **TGAI GO 支持训练**（作为引擎能力，不只是推理）
- 拿到"核显训练到底多慢"的**实测数据**（而不是推算）
- 为将来"端侧微调"（on-device fine-tuning）打基础 —— 这才是真正的应用场景

### 🎯 真正有价值的应用方向（建议）

**端侧微调（On-device Fine-tuning）** 而非从零训练：
```
场景：用户手机上用 TGAI CHAT，想让模型学自己的说话风格
做法：LoRA 微调，只训低秩矩阵（原模型冻结）
显存：50M 模型 + LoRA(r=8) ≈ 0.75 GB 静态 ⇒ 核显完全够
带宽：只读原模型权重（100 MB/token）但只写少量梯度
⇒ 这才是核显/端侧训练的现实意义
```

**LoRA 让训练内存降 10 倍以上**，而且核显的带宽劣势被"只读不写"部分抵消。

## 四、如果要动手，技术要点

### 4.1 反向传播需要的内核

| # | 内核 | 说明 | 复杂度 |
|---|---|---|---|
| 1 | 前向已有 | BF16 矩阵乘（split-K 版已验证）| ✅ |
| 2 | **dX = dY × W^T** | 数据梯度 | 中（矩阵乘变体）|
| 3 | **dW = X^T × dY** | 权重梯度 | 中 |
| 4 | **原子累加 dW** | 用 `VK_EXT_shader_atomic_float` | 低（扩展已支持）|
| 5 | **Adam 更新** | 读 w/g/m/v，写 w/m/v | 低 |
| 6 | **反向 RMSNorm / SiLU / RoPE** | 逐元素+归约 | 低 |
| 7 | **反向 Attention** | softmax 反向 + 两个矩阵乘 | 中高 |
| 8 | **反向 MoE 路由** | top-k 的梯度回传（稀疏）| 中 |
| 9 | **Loss scaling** | 混合精度防下溢 | 低 |

### 4.2 必须避开的坑（我预判）

| # | 风险 | 说明 |
|---|---|---|
| 1 | **原子浮点非确定性** | 每次运行结果可能末位不同 ⇒ 训练可复现性差。要确定性需固定规约顺序 |
| 2 | **BF16 梯度精度不足** | 训练通常用 FP32 梯度累加 + BF16 主权重（混合精度），不能全 BF16 |
| 3 | **共享内存 capacity** | 核显共享内存小（通常 32~64 KB/工作组），Attention 反向要大块 |
| 4 | **无 cooperative_matrix** | 没有矩阵加速单元，只能靠 FMA ⇒ 算力受限 |
| 5 | **驱动超时（TDR）** | 单个 dispatch 超 2 秒会被驱动杀掉（Windows 默认 TdrDelay）⇒ 要分块提交 |

**坑 5 我在本轮已撞过**：早期 46 GFLOP/s 的假数据就是因为分派维度错导致"只算了 1/256 的工作量"。

## 五、诚实的结论表

| 问题 | 答案 |
|---|---|
| 核显能训模型吗？ | **能**（显存到 100M，原子浮点扩展支持）|
| 训得动吗？ | **训得动，但极慢**（1B token 要 2 个月）|
| 比 CPU 快吗？ | **不一定** —— CPU 内存带宽 8.6 GB/s vs 核显 7 GB/s |
| 比云端快吗？ | **慢 200~1000 倍** |
| 值得做生产训练吗？ | **不值得** |
| 值得做实验吗？ | **值得** —— 验证引擎能力 + 为端侧微调铺路 |
| 最有价值的训练场景？ | **端侧 LoRA 微调**（只训低秩矩阵，内存降 10 倍）|

## 六、给你的选择

| 方案 | 内容 | 工作量 | 价值 |
|---|---|---|---|
| **A. 不做训练** | 专注推理内核 + 多厂商兼容（原计划）| 0 | 高（主线不偏）|
| **B. 做最小闭环实验** | 反向传播内核 + 10M 玩具模型 + 实测数据 | 4~7 天 | 中（探索性）|
| **C. 直接做端侧 LoRA** | 前向 + LoRA 反向 + Adam（跳过大模型反向）| 2~3 天 | **高（有真实场景）** |

**我推荐 A → C**：先把推理主线做完（RMSNorm/RoPE/Attention + 接线），
然后做 **端侧 LoRA 微调**（方案 C）—— 这才是核显/端侧训练真正有意义的用法。

**方案 B 的"玩波大的"我理解**，但数据摆在这里：**两个月训一个 50M 模型**，
而且**本机 CPU 可能还更快**。这个"大"玩不出效果。
