# B: MoE 性能优化 —— 实测分析与方案（2026-10-09）

**结论先行**：瓶颈在**并行效率**（只发挥 35% 可用带宽），不在内核算法。

---

## 一、瓶颈量化（全部本机实测）

### 1.1 每 token 需要读多少权重

模型 `_phone_v1q4.tg`：20 层 / 4 专家 top-2 / d=896 / dff=3584 / Q4_0

```
单个专家 w1+w2+w3 = 5.17 MB
每层激活 2 专家     = 10.34 MB
20 层 MoE 权重/token = 206.7 MB
```

### 1.2 实测带宽 vs 可用带宽

| 项目 | 数值 |
|---|---|
| decode 实测 | 15 tok/s ⇒ 66.7 ms/token |
| ⇒ 有效带宽 | 206.7 MB / 66.7 ms = **3.03 GB/s** |
| 本机顺序拷贝（读+写） | 21.1 GB/s |
| **裸测读带宽 1 线程** | **2.54 GB/s** |
| **裸测读带宽 4 线程** | **8.60 GB/s** |
| 裸测读带宽 8 线程 | 32.83 GB/s |

**⇒ 4 线程下可用 8.60 GB/s，引擎只用 3.03 GB/s ⇒ 利用率 35%。**

### 1.3 单核上限的意义

**单核读带宽只有 2.54 GB/s** ⇒ 内存**延迟受限**（不是容量带宽受限）。
⇒ **每个线程必须有足够多的"在途"未完成读请求（MLP）才能跑满带宽。**

这解释了为什么：
- 4→8 线程掉 29%（同步开销 + 调度）
- 多行内核收益不稳定（行访问模式改变影响预取）

## 二、内核微基准（tools/bench_moe.c）

| 专家形状 | V0 逐行 | V1 4行 | V2 8行 |
|---|---|---|---|
| **`[dff=3584, d=896]`（w1/w2）** | 2.267 ms | 0.89x | **1.10x** |
| **`[896, 3584]`（w3）** | 2.637 ms | 1.53x | **1.77x** ✅ |

**⇒ 结论**：
- **w3** 行短（3584 元素 = 14 KB）、行数少（896）⇒ 多行内核**有效（1.77×）**
- **w1/w2** 行多（3584）、每行仅 896 元素（3.5 KB）⇒ 多行内核**基本无效（1.10×）**

**⇒ 应选择性应用，不是全局替换。**

### 2.1 权重文件布局（实测，已是最优）

```
(0,'w1') off=18592736  len=1806336
(0,'w2') off=20399072              ← 偏移差 = 恰好 1806336 ⇒ 连续
(0,'w3') off=22205408
(1,'w1') off=24011744              ← 下一个专家紧接
```

**⇒ 无需重排（packing）**：同一专家的 w1 已是 3584 行连续存储，行步长 3584 字节，顺序流。
我之前担心的"专家权重分散"问题**在这个模型上不存在**。

## 三、优化方案（按优先级）

### P1 ★ 提高 MLP（内存级并行）—— 预期收益最大

**问题**：单核 2.54 GB/s 说明每核在途读请求太少。当前 `moe_w12_worker(nn)` 每个任务
只做 1 行点积（读 3.5 KB），做完就等下一个任务 ⇒ 读请求不能重叠。

**做法**：每个 worker 任务处理**多行**（如 4 行），让 4 个独立的 3.5 KB 读同时在途：

```c
/* 现在：一次 1 行 */
A->a[nn] = tg_dot(A->xt, A->w1 + nn*d, d);

/* 改为：一次 4 行（4 个独立读流同时在途） */
/* 用 dot4 内核 + 任务粒度 nn += 4 */
```

**为什么这次可能有效**（与我之前失败的"8 行"不同）：
- 之前失败是在 `_matmul_n_worker`（外层权重，行有跨页步长）
- **这里是 MoE 专家权重，行是连续的** ⇒ 4 个读流是 4 条连续流，预取器能处理

**微基准已证实**：w3 形状 4 行 = 1.53×、8 行 = 1.77×。
**w1/w2 形状收益小（1.10×）** ⇒ 只对 w3 应用，或两处都试后按实测决定。

### P2 提高任务粒度（减少同步次数）

**问题**：`tg_parallel(dff, ...)` 把 3584 行分给 nt+1 个块，每块 ~700 行。
每层 MoE 有 `moe_expert_w12` + `moe_expert_w3` 两次并行，×top-2 专家 = 4 次/层，
×20 层 = **80 次/ token**。每次都有锁 + 条件变量开销。

**做法**：把「一个专家的 w1+w2 计算」打包成**一次**并行调用（而不是两次），
或者把「同一 token 的 top-2 专家」合并成一次并行（4 个矩阵一起）。

### P3 无锁/自旋任务分发

**我已经做了部分**（原子完成计数 + 只唤醒主线程 + 自旋等待），
但**效果未在稳定环境验证**。建议在负载干净的机器上复测。

### P4 减少读取字节数（最彻底）

**206.7 MB/token 是硬成本**。要降低只能：
- **更激进的量化**：Q4_0 → Q3_K/Q2_K（llama.cpp 有），或
- **专家缓存**：MoE 路由有局部性，热点专家缓存在更快存储
- **投机解码**：一次前向出多个 token

**⇒ 这是 V3 阶段该做的事**（V3 是 7B MoE，权重读取成本更高）。

## 四、给 V3 的启示（重要）

V3 设计：**7B MoE（8 专家 top-2）+ 64K 上下文 + 96K 词表 + CSA/GQA 混合注意力**

| V3 特性 | 对 TGAI GO 的影响 | 需提前准备 |
|---|---|---|
| **96K 词表** | 嵌入矩阵 96K×d，LM head 每 token 读全表 | **vocab hash 已做（A）**；LM head 需多线程（已有）|
| **64K 上下文** | KV cache 4× 于 8K ⇒ 内存压力大 | **KV cache 量化**（llama.cpp 有 `--cache-type`）|
| **CSA 压缩稀疏注意力** | 新注意力模式，3:1 与全局层交替 | 需要新增层类型 |
| **Attention Residuals** | 跨层门控聚合 | 需要保存前层表示 |
| **aux-loss-free 负载均衡** | **V3 用这个** ⇒ `_qb_bias` 语义一致 | ✅ **已实现**（本轮）|
| **RoPE θ=500K** | 长上下文外推 | 已有 NTK-by-parts |
| **Muon 优化器** | 只影响训练 | — |
| **FP4 QAT** | 推理需要 MXFP4 支持 | V3.1 |

**⇒ 最该提前做的三件**：
1. **KV cache 量化**（64K 上下文的必需品）
2. **CSA/GQA 混合注意力的层调度框架**
3. **Attention Residuals 的表示缓存**

## 四点五、★ B-P1 实施与实测结果（已回退）

**已实施**：`moe_expert_w3` 改用 4 行内核（`tg_parallel_stride(d4, 4, ...)` + 余数收尾）。

**严格 A/B 实测**（每档 5 次取中位数，独立进程，输出一致性已验证）：

| threads | prew3（逐行）| moew3（4行）| 提速 |
|---|---|---|---|
| 1 | 5.4 tok/s | 5.8 | **1.07x** |
| 2 | 5.5 | 5.5 | 1.00x |
| 4 | 5.4 | 5.3 | 0.98x |
| 8 | 6.5 | 5.5 | **0.85x** |
| token 输出 | — | — | ✅ 全部一致 |

**⇒ 判定：无效，已回退。**

### 为什么无效（数学上必然）

微基准里 w3 快 1.53×，但 **w3 只占 MoE 计算的约 21%**：

```
w1: dff×d = 3584×896 = 3.21M MAC
w2: dff×d = 3584×896 = 3.21M MAC
w3: d  ×dff = 896×3584 = 3.21M MAC    ← 三者相等！
```

等等 —— 三者 MAC 数相同（都是 3.21M），所以 w3 占 1/3。

但实测端到端只有 1.07×：`1/(2/3 + 1/3/1.53) = 1.15×` 是理论上限，
实测 1.07× 说明**局部收益被摊薄后基本消失**，且 8 线程下因 stride 改变了
任务分块方式而**反而更差（0.85x）**。

**⇒ 教训**：**不要在单一组件上做局部优化**，除非先确认它是主瓶颈。
本机真正的瓶颈是 §一的**整体带宽利用率（35%）**，而非某个矩阵乘的核效率。

### 更根本的方向（B 的正确解法）

| 方向 | 原理 | 预期 |
|---|---|---|
| **减少读取字节** | 更激进量化（Q4_0→Q2_K/Q3_K，llama.cpp 有）| **最直接**：字节数减半 = 速度近翻倍 |
| **专家缓存（LRU）** | MoE 路由有局部性，热点专家缓存在更快层 | 中 |
| **投机解码** | 一次前向出多 token | 大，但工程复杂 |
| **提高 MLP** | 每线程多发在途读请求 | 需重构任务粒度（不是简单多行）|

**⚠️ 明确不要做的事**：继续在单个 matmul 内核上微调。
微基准（2.4~4.3 GFLOP/s）已经说明是**内存带宽受限**，
而带宽利用率（35%）要靠**调度/量化**解决，不是靠指令级优化。
