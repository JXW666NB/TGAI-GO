# ★★ 重要发现：逐算子 GPU 桥接在 Vulkan 上是架构性错误

**日期**：2026-10-10
**结论**：**Vulkan 的每次 dispatch 开销约 100~500 µs，而 RMSNorm 的计算只需几 µs**
**⇒ 逐算子桥接注定比 CPU 慢，与优化无关。GPU 只能在"整个前向常驻设备"时才划算。**

---

## 一、实测数据（真实 V2.7 模型，80 tokens，temp=0）

| 版本 | CPU | GPU 桥 | 变化 | 输出一致 |
|---|---|---|---|---|
| **v1**（每次 alloc + 传输）| 10.70 tok/s | 4.00 tok/s | **−62.6%** | ✅ 逐字相同 |
| **v2**（缓冲池 + 权重常驻）| 11.20 tok/s | 5.80 tok/s | **−48.2%** | ✅ 逐字相同 |

**v2 的优化确实有效**（改善 14.4 个百分点），但**没解决根本问题**。

---

## 二、算一下为什么必然慢（数量级分析）

```
单次 RMSNorm 的工作量（TGAI V2.7）：
  输入: seq × d_model × 4 = 8 × 1024 × 4 = 32 KB
  计算: 8 × 1024 × 2 FLOP = 16 KFLOP
  核显算力（实测）: 370 GFLOP/s
  ⇒ 纯计算时间 = 16e3 / 370e9 = 0.043 µs   ← ★ 43 纳秒！

单次 Vulkan dispatch 的开销（实测经验值）：
  vkUpdateDescriptorSets        ~10-50 µs
  vkResetCommandBuffer +
  vkBeginCommandBuffer          ~5-20 µs
  vkCmdBindPipeline/Desc/…      ~5-20 µs
  vkEndCommandBuffer            ~2-5 µs
  vkQueueSubmit                 ~20-100 µs
  vkWaitForFences（同步等待）    ~50-300 µs   ← 大头
  ------------------------------------------------
  合计                          ~100-500 µs

对比：100 µs / 0.043 µs = 2325 倍
⇒ 即使 GPU 计算快 100 倍，净结果仍是慢 23 倍
```

**⇒ 这不是"优化不够"，是"用错了层次"。**

## 三、为什么核显上这个结论尤其致命

```
独显（如 4090）：
  算力 82 TFLOP/s ⇒ 同样的 16 KFLOP 只要 0.0002 µs
  ⇒ 单算子更不划算（但独显的价值在【大矩阵乘】，因为那有上亿 FLOP）

核显：
  算力 370 GFLOP/s（我实测的峰值）
  ⇒ 单算子只要数据量够大才有意义

关键判据（经验公式）：
  值得走 GPU 的条件:  FLOP / 设备算力  >  10 × dispatch开销
                    = 计算时间 > 1 ms（取 dispatch 100 µs 的 10 倍安全边际）

  RMSNorm (16 KFLOP)  → 0.04 µs  ❌ 差 25000 倍
  Attention (seq=512) → ~10 MFLOP → 27 µs  ❌ 差 37 倍
  专家矩阵乘 (8.4 MFLOP) → 23 µs  ❌ 差 4 倍
  ★ 整个前向 (28 层) → ~2.4 GFLOP → 6.5 ms  ✅ 划算！
```

## 四、正确的架构（这也解释了 llama.cpp 为什么那样做）

```
❌ 错误（我 v1/v2 的做法）：
   Python/C 引擎逐算子调用 → 每个算子一次 GPU 往返
   ⇒ N 个算子 × 100 µs 开销

✅ 正确（llama.cpp / 我该做的）：
   整个前向 = 一次 GPU 提交序列
   中间张量全部【常驻设备内存】，一次都不回主机
   ⇒ 只有输入 embedding 和输出 logits 各一次传输
   ⇒ dispatch 开销被"整批"摊薄
```

**llama.cpp 的 `llama_decode` 就是这么做的**：
一次调用把整个 graph（几十个算子）编进一个 command buffer 提交。

## 五、所以我该怎么做（修正路线）

| 方案 | 说明 | 工作量 |
|---|---|---|
| **A. 撤回逐算子桥接** | 承认错误，保留代码但设"最小数据量门槛"（如 ≥ 1 MB 才走 GPU）| 0.5 天 |
| **B. 改造为"整层/整前向 GPU 常驻"** | 把 28 层的权重全部上传设备，前向在图内跑完 | 5~8 天 |
| **C. 只接大矩阵乘** | 矩阵乘是 FLOP 密集的（seq 大时 67 MFLOP → 0.2 ms），仍有价值 | 2 天 |
| **D. 放弃 GPU 推理，专注其他** | 核显的算力/带宽本就不足 | 0 |

**我推荐 B**，理由：
- 这是唯一能真正利用 GPU 的架构（也是所有成熟推理引擎的做法）
- 我的 7 个内核**全部已验证**（BF16 矩阵乘 split-K 已验证 164 GFLOP/s）
- GPU 侧 KV cache 已做好（正好是"常驻"的一部分）
- 后端抽象层已做好（正好承载这个架构）

**B 的挑战**：
```
V2.7 权重 5.64 GB（BF16）
核显可用"显存" 7.25 GB
⇒ 权重能全部装下！ 剩 1.6 GB 给激活 + KV cache
⇒ ★ 技术上可行（这是我实测过的数字）
```

## 六、v1 → v2 的优化细节（虽然没救回来，但值得记录）

### v1 的问题

```c
int tg_gpu_try_rmsnorm(...) {
    void* dx = b->alloc(xb);      // vkCreateBuffer + vkAllocateMemory  重量级
    void* dw = b->alloc(wb);      // 同上（每次都重新分配！）
    void* dy = b->alloc(xb);      // 同上
    b->upload(dx, x, xb);
    b->upload(dw, weight, wb);    // ★ 权重每次都传（其实永不改变）
    b->rmsnorm(...);
    b->download(out, dy, xb);
    b->free(dx); b->free(dw); b->free(dy);   // vkDestroyBuffer + vkFreeMemory
}
```

### v2 的两项优化

```c
/* ① 缓冲池：按大小复用（12 槽）*/
void* dx = pool_get(xb);     // 命中就复用，免去 create/allocate
...
pool_put(dx);                // 不销毁，放回池

/* ② 权重常驻：指针作 key（模型加载后 weight 指针固定）*/
void* dw = wcache_get(weight, wb);   // 首次上传，之后命中（32 槽）
```

**效果**：−62.6% → −48.2%（改善 14.4 个百分点）

**但仍慢的原因**：省掉的是 alloc/free（~50 µs），
剩下 dispatch + 同步 + 传输（~150~400 µs）依然远超 0.043 µs 的计算。
