## 一、A：vocab hash 表 ✅ **完成，提速 1.3x ~ 358x**

### 改动
| 位置 | 内容 |
|---|---|
| `src/tgai_engine.c` | `TGModel` 加 `vocab_hash` / `vocab_hash_cap` |
| 同上 | `tg_fnv1a32()` + `vocab_hash_build()` + `vocab_hash_lookup()`（开放寻址，容量 2 的幂）|
| 同上 | 加载 tokenizer 后建表；编码时 O(1) 查，**未命中回落线性扫描**（保证正确性）|
| 同上 | `tg_free` 前释放 |

### 实测（`tools/bench_encode_breakdown.py`，严格 A/B 同一模型同一文本）

| 用例 | 无 hash | **有 hash** | 提速 |
|---|---|---|---|
| 纯ASCII短 (20B) | 7.0 µs | **1.9** | 3.6x |
| 纯ASCII长 (200B) | 56.2 | **5.5** | **10.1x** |
| 英文句子 | 13.3 | **2.3** | 5.8x |
| 纯中文短 | 31.1 | **1.6** | **19.2x** |
| **纯中文长 (120字)** | **861.7** | **5.2** | **164.6x** |
| 真实特殊标记 | 62.5 | **1.9** | **32.9x** |
| **长中文+标记** | **2214.4** | **6.2** | **358.1x** |

### 为什么中文收益巨大（关键洞察）
`vocab_hash_lookup` 只对**完整单元**命中。中文字符是 **3 字节**，而 V1 词表存的是
**单字节** token ⇒ 查表必然未命中 ⇒ **每个汉字都要全表线性扫描 32768 次**。
hash 让绝大多数查找直接命中，慢路径几乎不再触发。

### 一致性
分词验收 **0/11 不一致**（与 HF tokenizer 逐 token 一致）✅

## 二、B：MoE 优化 ⚠️ **瓶颈已量化，P1 实测无效已回退**

### 2.1 瓶颈量化（全部本机实测）

```
每 token MoE 权重读取 = 206.7 MB
实测 decode 15 tok/s ⇒ 66.7 ms/token
⇒ 有效带宽 3.03 GB/s

裸测读带宽: 1线程 2.54 GB/s / 4线程 8.60 GB/s / 8线程 32.83 GB/s
⇒ 引擎 4 线程只发挥 35% 可用带宽
⇒ 单核 2.54 GB/s 说明是【内存延迟受限】⇒ 关键在 MLP（内存级并行）
```

### 2.2 权重布局核实（重要发现：**无需 packing**）
```
(0,'w1') off=18592736  len=1806336
(0,'w2') off=20399072   ← 偏移差 = 恰好 1806336 ⇒ 连续
(1,'w1') off=24011744   ← 下一个专家紧接
```
**⇒ 同一专家的权重已是连续存储（行步长 = d*4），预取器友好。
我原本担心的"专家权重分散"在这个模型上不存在。**

### 2.3 内核微基准（`tools/bench_moe.c`）

| 专家形状 | 逐行 | 4行 | 8行 |
|---|---|---|---|
| `[dff=3584, d=896]`（w1/w2） | 2.267 ms | 0.89x | 1.10x |
| `[896, 3584]`（w3） | 2.637 ms | **1.53x** | **1.77x** ✅ |

### 2.4 B-P1 实施与实测（**已回退**）

对 w3 应用 4 行内核（`tg_parallel_stride(d4, 4, ...)`）：

| threads | prew3 | moew3(4行) | 提速 |
|---|---|---|---|
| 1 | 5.4 | 5.8 | 1.07x |
| 2 | 5.5 | 5.5 | 1.00x |
| 4 | 5.4 | 5.3 | 0.98x |
| 8 | 6.5 | 5.5 | **0.85x** |
| token 输出 | — | — | ✅ 一致 |

**⇒ 无效，已回退。** 原因：局部优化被摊薄（w3 只占 MoE 的 1/3，
理论上限 1.15x，实测 1.07x），且 8 线程下 stride 改变分块方式反而更差。

### 2.5 B 的正确方向（结论）

| 方向 | 原理 | 预期 |
|---|---|---|
| **减少读取字节** | 更激进量化（Q4_0→Q2_K/Q3_K）| **最直接**：字节减半 ≈ 速度翻倍 |
| 专家缓存（LRU）| MoE 路由有局部性 | 中 |
| 投机解码 | 一次前向多 token | 大但复杂 |
| 提高 MLP | 每线程多发在途读 | 需重构任务粒度 |

**⚠️ 明确不要做**：继续微调单个 matmul 内核。微基准（2.4~4.3 GFLOP/s）已证明是
**带宽受限**，要靠**调度/量化**解决。

```
   BF16 量化相对误差 0.3152%（bf16 尾数 7 位 ⇒ 理论 ~0.39%，符合）
② 引擎加载含 BF16 权重的 .TG: ✅ 成功（DTYPE_BF16 被识别）
   引擎 BF16 解码 vs torch 参考: ✅ 逐位完全一致
```

### ★ 踩到的坑（写进代码注释了）
**numpy 没有 bfloat16 dtype** ⇒ `weight.to(torch.bfloat16).numpy()` 会报
`module 'numpy' has no attribute 'bfloat16'`。
**解法**：`w.view(torch.uint16).numpy().tobytes()`（取位模式）。

### 5.1 V3 架构要点（"全新架构与特效"）

| 项 | V2.7（当前）| **V3** |
|---|---|---|
| 词表 | 32,779 | **96K**（自训中文 BPE）|
| 上下文 | 8K | **64K**（原生）|
| RoPE θ | 10,000 | **500,000** |
| 层数 | 28 | **20** |
| 注意力 | 标准 | ★ **混合：3 层 CSA 压缩稀疏 + 1 层全局 GQA**（KV 低秩压缩 MLA 式）|
| MoE | 8 专家 top-2 | **8 专家 top-2** + ★ **aux-loss-free 负载均衡** |
| ★ 新增 | — | ★ **Attention Residuals（AttnRes）**：跨层直连残差门控聚合 |
| 优化器 | — | **Muon**（V3.0 采用）|
| 待评估 | — | FP4 QAT、MTP（多 token 预测）、mHC |
| 路线 | 自回归 | ★ **自回归为主**；DLLM（扩散）**仅独立研究分支** |

### 5.2 ★ 对 TGAI GO 的关键启示

| V3 特性 | 对推理引擎的影响 | 我们的准备 |
|---|---|---|
| **aux-loss-free 负载均衡** | **就是 `_qb_bias` 的语义来源**（DeepSeek 方案）| ✅ **本轮已实现并验证** |
| **96K 词表** | LM head 每 token 读全表；编码查表量大 | ✅ **A 的 vocab hash 正好解决** |
| **64K 上下文** | KV cache 是 8K 的 8 倍 | ⬜ **需 KV cache 量化**（llama.cpp 的 `--cache-type`）|
| **CSA/GQA 混合注意力** | 需新增层类型 + 3:1 调度 | ⬜ 需新内核 |
| **Attention Residuals** | 需保存并门控聚合前层表示 | ⬜ 需表示缓存 |
| **RoPE θ=500K** | 长上下文外推 | ✅ 已有 NTK-by-parts |
| **BF16 原生** | 转换精度 | ✅ **C 已完成** |

### 5.3 V3 给我们的三个"必做前瞻项"
1. **KV cache 量化**（64K 的必需品）—— 否则显存/内存放不下
2. **CSA/GQA 混合注意力的层调度框架** —— 3:1 交替是 V3 的核心结构
3. **Attention Residuals 的表示缓存** —— 跨层门控需要额外 buffer

### 5.4 有趣的旁证：V3 文档自己否定了扩散路线
V3 计划书 §十明确写：
> **"并行更快"是神话**：LLaDA/Dream 实测比同质 AR 更慢（KV 缓存失效是致命伤）
> **工具调用系统性失败**：扩散噪声下无法保持 JSON schema 精度
> **结论：V3 主架构坚定自回归，DLLM 作为独立研究分支小规模验证**

**⇒ 与我们的推理优化方向（自回归 + KV cache + MoE）一致。**
