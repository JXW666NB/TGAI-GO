# 🔴 TGAI GO 的 BPE 分词与训练不一致 —— 根因分析与修复方案

**日期**：2026-10-09
**发现者**：DSH agent（实测）
**触发**：同事在 llama.cpp 侧确认 V2.7 的乱码/复读根因是「**转换模式错 ⇒ 编码偏离训练**」。
我据此回头审计 TGAI GO，**发现了同一类病，而且更严重**。

---

## 一、🚨 实测证据（决定性）

用引擎的 `tg_encode` 与 HuggingFace tokenizer（训练用的那个）对同一批文本编码：

| 文本 | 引擎 `tg_encode` | HF tokenizer | 判定 |
|---|---|---|---|
| `你好` | `[2, 911, 2002, 3]` | `[911, 2002]` | ❌ |
| `1+1是多少？` | `[2, 26, 20, 26, 3251, 1956, 2243, 8326]` | `[26, 20, 26, 3251, 1956, 2243, 8326]` | 仅差 BOS/EOS |
| **`TGAI`** | **`[2, 61, 48, 42, 50, 3]`** | **`[24651, 10323]`** | ❌ **拆成 4 个字节 token！** |
| `什么是TGAI` | `[2, 819, 754, 3251, 61, 48, 42, 50]` | `[819, 754, 3251, 24651, 10323]` | ❌ |
| `Hello world` | `[2, 49, 78, 85, 85, 88, 96, 88]` | `[24751, 9, 9009]` | ❌ |
| `def f(x): return x+1` | `[2, 77, 78, 79, 79, 17, 97, 18]` | `[10096, 9, 79, 17, 97, 9927, 9, 10314]` | ❌ |
| `<用户>\n你好\n<TGAI><回答>\n` | `[2, 37, 4644, 2833, 39, 911, 2002, 37]` | `[32770, 8, 911, 2002, 8, 32771, 32773, 8]` | ❌ **特殊标记未识别** |
| `2026年10月9日` | `[2, 27, 25, 27, 31, 2454, 26, 25]` | `[23181, 2454, 8493, 3327, 34, 3210]` | ❌ |

```
⇒ 10/10 条不一致
```

**这是"编码偏离训练"，与 llama.cpp 侧同事发现的病**完全同类** ⇒ 必然导致复读/乱码。**

### ⚠️ 诚实说明（避免误导）
上面测的是 `_phone_v1q4.tg`（**V1 老模型，本来就没有 merges**，见 §三）。
所以这组数据**不能直接代表 V2.7**。但它确凿证明了：
**只要 `.TG` 里没有 merges，引擎就会退化成字符/字节级分词** —— 而转换器【写死了不写 merges】（见 §二）。

## 二、根因 1：转换器**故意禁用了 BPE**（已修 ✅）

### 原代码（`tools/tgai_convert.py` L154-166）

```python
buf += struct.pack('<I', vocab_size)
# ─── BPE merges 禁用说明 ─────────────────────────────────
# TGAI 原生模型训练时用 ChineseTokenizer, 其 _hf 因 hf_path 相对路径
# 问题未加载 (os.path.exists 找不到文件), 走字符级回退路径:
#   "你好" → '你'(911) + '好'(2002) → [911, 2002] (不合并)
# 如果 .TG 写入 merges, C 引擎 bpe_apply 会做 BPE 合并:
#   "你好" → '你好'(13036) → [13036] (合并)
# 编码和训练时不一致 → CLI/手机端乱码 (GUI 用 ChineseTokenizer 正常)
# 所以 n_merges=0, C 引擎 bpe_apply 直接返回, 用字符级分词。
buf += struct.pack('<I', 0)  # n_merges=0, 禁用 BPE 合并
```

**⇒ 为了让"当年 hf_path 没加载成功"的旧模型能跑，转换器永久关掉了 BPE。**

**但对 V2.7 这个假设是错的**：V2.7 训练**确实用了 HF BPE**（同事已实测 merges 生效）。

### 已修复

`tools/fix_converter_merges.py`：
1. 加 `_load_token_merges()`：按优先级取 merges
   - 顶层 `merges`（TGAI 打包格式，元素是 `"a b"` 字符串）
   - 否则从 `hf_path` 指向的 HF 文件取 `model.merges`（元素是 `[a,b]`）
2. 有 merges 就写入，**没有才维持旧的 `n_merges=0`**（老模型不受影响）

**实证**：
```
id_to_token 项数: 32779
取到 merges: 24355 条
HF 期望条数: 24355
⇒ ✅ 与 HF 完全一致
```

**V2.7 词表数据完整**：
| 来源 | 内容 |
|---|---|
| `tokenizer_v3tok.json` 顶层 | `merges` = 24,355 条 |
| `tokenizer_hf_v3tok.json` | `model.type=BPE`, `model.merges` = 24,355 条 |
| 特殊标记 | `<用户>`=32770 `<TGAI>`=32771 `<思考>`=32772 `<回答>`=32773 `<系统>`=32774（都在 vocab）|
| `space_token` | `'▁'` |
| `pre_tokenizer` | `[\u4e00-\u9fff\u3400-\u4dbf\uf900-\ufaff]\|[A-Za-z]+\|[0-9]+\|\s+\|[!-/:-@\[-`{-~]+\|[^\sA-Za-z0-9]` |

## 三、根因 2：为什么老模型没有 merges（解释，非 bug）

`_phone_v1q4.tg` 的 tokenizer 段探查：
```
vocab_size = 32768
merges     = 0 条（搜索 24355 找不到）
段首 token 文本: <PAD> <UNK> <BOS> <EOS> <IMG> <AUD> <VID> ...
```
⇒ V1 时代的模型**本身就是字符级 tokenizer**，没有 merges 是正常的。
引擎对它的编码（字符级）**与它自己的训练一致** ⇒ **这个老模型没问题**。

**⇒ 结论：merges 有没有，取决于模型。转换器现在能正确区分了。**

## 四、根因 3：特殊标记（`<用户>` 等）不被识别为单 token ✅ **已修**

### 问题

引擎的 `tg_encode`（`src/tgai_engine.c` L2903-2970）：
```c
/* 切分为 UTF-8 字符, 每个字符查 vocab 得到初始 token id */
while (p < end) {
    int cl = utf8_char_len(*p);
    /* 跳过 ASCII 空白（注释说与 Python Whitespace pre_tokenizer 一致）*/
    if (cl == 1 && (*p==' '||*p=='\t'||*p=='\n'||*p=='\r')) { p += cl; continue; }
    /* 查找单字符 token */
    int tid = -1;
    for (int i = 0; i < model->vocab_size; i++) {          /* ← O(vocab) 线性扫描！*/
        if (strcmp(model->vocab[i], char_buf) == 0) { tid = i; break; }
    }
    ...
}
```

**⇒ 它把文本按 UTF-8 字符切开再逐字符查表，从不检查"这段文本是不是一个特殊标记"。**

**后果**：`<用户>` 被编成 `[37, 4644, 2833, 39]`（`<`/`用`/`户`/`>`）
而不是单个 token `32770` ⇒ **V2.7 的 9 标记对话格式在 TGAI GO 上完全失效**。

### 修复设计（需要改 .TG 格式 + 引擎）

**方案 A（推荐，与 llama.cpp 的 `parse_special` 对齐）**：把特殊标记表写进 `.TG`

1. **`.TG` 格式扩展**：tokenizer 段末尾追加 `n_special` + `(id, len, text)` 列表
   （用 header 的 `extension_off` 字段，或直接追加在 `eos_id` 之后；
   老引擎读到段末即停，**向后兼容**）
2. **引擎加载时**读出特殊标记表
3. **`tg_encode` 开头先做一次贪心最长匹配**：
   ```
   在当前位置，尝试匹配特殊标记表里最长的条目
     命中 ⇒ 直接输出该 id，跳过该段文本
     未命中 ⇒ 走原来的字符切分 + BPE
   ```
4. **`tg_decode` 的 `skip_special`** 已有，无需改

**方案 B（临时，不改格式）**：在 Python 层 `tgai_chat.py` 里手工拆分特殊标记，
逐段调用 `tg_encode` 再拼接。**缺点**：性能差、且要求调用方知道所有标记。

**⇒ 建议走方案 A。**

## 五、根因 4：pre_tokenizer 不匹配（V2.7 专属）✅ **已修（阶段1）**

| | 老模型（V1）| **V2.7** |
|---|---|---|
| pre_tokenizer | Whitespace（丢弃空白）| **正则**：`[\u4e00-\u9fff...]\|[A-Za-z]+\|[0-9]+\|\s+\|...` |
| space_token | — | **`'▁'`** |

**引擎当前行为**：**丢弃所有 ASCII 空白**（L2935-2941）。

**V2.7 训练时的行为**（正则 pre_tokenizer + `▁`）：
- `\s+` 规则把连续空白当作**一个可合并单元**，最终编码成 `▁` 相关 token
- 实测 HF：`'Hello world'` → `[24751, 9, 9009]`，其中 **`9` 就是空白 token**

**⇒ 引擎丢空白，HF 把空白编成 token 9 ⇒ 必然不一致。**

**修复设计**：
1. 把 `pre_tokenizer` 正则与 `space_token` 也写进 `.TG`（同方案 A 的扩展段）
2. 引擎按正则切分后再做 BPE（而不是简单按字符切）
3. 若不实现正则（工作量大），**至少**：把空白替换成 `space_token` 参与 BPE，
   而不是直接丢弃

**⚠️ 这条直接决定 V2.7 能否在 TGAI GO 上正常工作。**

## 六、根因 5：编码器性能（附带发现）⬜ **待修**

```c
for (int i = 0; i < model->vocab_size; i++) {     /* 32779 次 strcmp */
    if (strcmp(model->vocab[i], char_buf) == 0) { tid = i; break; }
}
```

**每个字符都要全表线性扫描 32779 次 `strcmp`。**

- prompt 100 字符 ⇒ **~327 万次 strcmp**
- 实测：`tg_encode` 对短文本就有可观开销

**修复**：加载时建一张 **hash 表**（`name → id`）。
引擎已有 `find_weight` 用的 `fnv1a_64` hash 基础，可直接复用思路：
```c
/* 加载时 */
m->vocab_hash = 建表(vocab, vocab_size);   /* 开放寻址，容量取 2 的幂 > 1.5*vocab */
/* 编码时 */
tid = vocab_lookup(m, char_buf, cl);       /* O(1) */
```
**预期**：编码阶段提速 10× 以上。

### 🐛 过程中发现并修掉的一个隐蔽 bug

**错误实现**：

    p += (cl == model->space_len && model->space_len > 0) ? 1 : cl;

**中文 UTF-8 长度 = 3，而空格替换字符 ▁ 的字节长度也是 3** ⇒ 中文被误判为
「发生过空格替换」⇒ 指针只前进 1 字节 ⇒ `你`(E4 BD A0) 被拆成 `[E4][BD][A0]`，
后两字节是孤立续字节 ⇒ **UNK** ⇒ 实测每个中文字后面都冒出 `[1, 1]` 两个 UNK。

**修法**：引入独立的 `src_len` 记录「源文本消费字节数」，与查表用的 `cl` 解耦。

### 仍未做（下一步）

1. **完整的正则 pre_tokenizer 复刻** —— 当前实现是「按 UTF-8 字符切 + 空格替换」，
   已在 11 条测试上验证一致；但**极端情况**（连续多空格、制表符、混合标点）
   需按正则 `[\u4e00-\u9fff...]|[A-Za-z]+|[0-9]+|\s+|[!-/:-@\[-`{-~]+|[^\sA-Za-z0-9]`
   的 `Isolated` 语义再对齐。**建议扩充测试集覆盖这些边界。**
2. **vocab hash 表**（性能）—— 当前每字符仍做 O(vocab)=32779 次 `strcmp`。
3. **BOS/EOS 语义**：V2.7 的 `post_processor` 是 `null` ⇒ 调用 `tg_encode` 时应传
   `add_special=0`。而 `tgai_chat.py` 的 `build_prompt` 对 TGAI 原生模型传的是
   `add_bos=True` ⇒ **需一并改掉**（属 P0-2 的 chat 层修复）。
