**日期**：2026-10-10

## 一、接线设计（低风险优先）

### 为什么独立成文件

```
直接改 tgai_engine.c（157 KB / 3620 行）里的 rmsnorm/rope/attention 风险高
⇒ 接线逻辑单独放 tgai_gpu_bridge.c，引擎只在关键位置调一次 tg_gpu_try_*()
   返回 1 = GPU 完成；返回 0 = 走原有 CPU 路径
```

### 开关（关键设计）

```c
TGAI_USE_GPU=0 或未设（默认）⇒ 所有 tg_gpu_try_* 立即返回 0 ⇒ 零行为变化
TGAI_USE_GPU=1              ⇒ 尝试 GPU；失败自动回落 CPU
```

**默认关闭的理由**：稳定性第一 —— 新路径先验证，再考虑改默认。

### 接线示例（引擎里的实际代码）

```c
static void rmsnorm(float* out, const float* x, const float* weight,
                    int seq, int d, float eps) {
    /* ★ GPU 快速路径（默认关闭；TGAI_USE_GPU=1 启用）
     *   返回 1 = 已由 GPU 完成 ⇒ 直接 return
     *   返回 0 = 不可用/失败 ⇒ 落到下面的 CPU 实现（原逻辑一字未改）*/
    if (tg_gpu_try_rmsnorm(out, x, weight, seq, d, eps)) return;
    for (int t = 0; t < seq; t++) {
        ... 原有 CPU 实现，完全未改 ...
    }
}
```

**注意**：CPU 实现**一字未改** —— 只是前面加了一行 try。

## 二、验证结果（实测）

### ① 默认路径（未设 TGAI_USE_GPU）

```
tg_gpu_init() = 0   enabled=0
原因: TGAI_USE_GPU 未开启（设为 1 启用 GPU 加速）
未启用时算子返回: rmsnorm=0 silu=0 softmax=0
⇒ ✅ 未启用时全部返回 0（CPU 路径不受影响）
```

**这是"不破坏现有功能"的归零验证** —— 三个算子全部返回 0，
引擎必然走原 CPU 路径 ⇒ 与接线前逐位相同。

### ② 启用 GPU（TGAI_USE_GPU=1）

```
tg_gpu_init() = 1   enabled=1
未启用时算子返回: rmsnorm=1 silu=1 softmax=1
⇒ ✅ 三个算子都走了 GPU

[2] GPU 算子 vs CPU 参考:
    RMSNorm   err=2.253e-07  不符=0/8192  ✅
    SiLU*Mul  err=3.169e-07  不符=0/4096  ✅
    Softmax   err=8.410e-07  不符=0/8192  ✅

[3] 确定性（同一输入连续 5 次）:
    5 次结果逐位相同 ✅（无竞态）

桥接统计: calls=12 fallbacks=0
```

### ③ 编译验证（三种模式）

```
ENG_CPU_EXIT=0    引擎不带 GPU 桥（纯 CPU）
ENG_GPU_EXIT=0    引擎带 GPU 桥
```

## 三、遇到的问题（诚实记录）

### 坑 13：测试没定义 `TG_BE_HAS_VULKAN`

```
现象: TGAI_USE_GPU=1 时仍报「auto 选到了非 GPU 后端（cpu）」
根因: 编译桥接层时漏了 -DTG_BE_HAS_VULKAN
      ⇒ tg_backend_vulkan.init == NULL
      ⇒ auto 探测跳过 vulkan ⇒ 选到 cpu
修法: 编译命令补上定义
教训: 条件编译宏漏一个，功能"静默失效"而不报错
```

### 坑 14：测试逻辑本身有缺陷

```
现象: GPU 启用后测试报「❌ 有算子返回了 1（可能误走 GPU）」
根因: 测试断言写死"必须返回 0"，没区分"启用/未启用"两种情况
修法: 按 enabled 分支判断
      enabled=0 ⇒ 必须全 0（CPU 路径不变）
      enabled=1 ⇒ 应全 1（确实走 GPU）
教训: 测试的断言要跟着"被测量"变化，不能写死
```

## 四、已接线 vs 待接线

| 算子 | 内核已验证 | 已接线到引擎 | 说明 |
|---|---|---|---|
| **RMSNorm** | ✅ | ✅ | `tg_gpu_try_rmsnorm` |
| **SiLU × Mul** | ✅ | ✅ | `tg_gpu_try_silu_mul` |
| **Softmax** | ✅ | ✅ | `tg_gpu_try_softmax` |
| RoPE | ✅ | ⬜ | 需在引擎 rope() 里接线（含 KV cache 写入，较复杂）|
| Attention | ✅ | ⬜ | 需改造 tg_forward 的注意力段 |
| MoE 路由 | ✅ | ⬜ | 需在 moe forward 里接线 |
| BF16 矩阵乘 | ✅ | ⬜ | 引擎的 matmul 路径有多条（Q4/BF16/FP32），接线需谨慎 |

**⇒ 7 个内核全部验证通过；其中 3 个已接线并验证。**

## 五、剩余工作（明确的下一步）

| # | 项目 | 复杂度 | 说明 |
|---|---|---|---|
| 1 | RoPE 接线 | 中 | 引擎的 `rope()` 是纯 CPU 实现（L2749），需处理 cos/sin 表上传与 KV cache 布局 |
| 2 | Attention 接线 | **高** | 引擎把 attention 写在了 `tg_forward` 内部（融合实现），要拆出来才能替换 |
| 3 | MoE 路由接线 | 中 | 需在 `moe_forward` 里替换 top-k 逻辑 |
| 4 | BF16 矩阵乘接线 | **高** | 引擎有 `matmul_bf16` / `_matmul_impl_bf16` 多条路径 + 多线程并行，替换要保证不破坏并行 |
| 5 | 端到端回归 | 中 | 加载真实 V2.7 模型，对比 CPU/GPU 两种模式的输出 token 是否一致 |

**诚实评估**：剩下 4 项接线中，Attention 与矩阵乘是**深度改造**（引擎里是融合实现 +
多线程并行），不是加一行 try 能解决的。预估 3~5 天，且需要充分的回归测试。

## 七、复现命令

```bat
:: 编译（三种模式）
set VCVARS=C:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\VC\Auxiliary\Build\vcvars64.bat
call "%VCVARS%"

:: 纯 CPU 引擎
cl /c /O2 /arch:AVX2 /fp:fast /utf-8 /std:c11 /I src src\tgai_engine.c /Fo:build\eng_cpu.obj

:: 带 GPU 桥的引擎
cl /c /O2 /arch:AVX2 /fp:fast /utf-8 /std:c11 /DTG_GPU_BRIDGE_ENABLED /I src /I third_party ^
   src\tgai_engine.c /Fo:build\eng_gpu.obj

:: 桥接验证程序
cl /O2 /utf-8 /std:c11 /DTG_GPU_BRIDGE_ENABLED /DTG_BE_HAS_VULKAN /I src /I third_party ^
   tests\test_gpu_bridge.c src\tgai_gpu_bridge.c src\tgai_backend.c ^
   src\tgai_vk_kernels.c src\tgai_vulkan.c third_party\vulkan\volk.c ^
   /Fe:_gb.exe

:: 跑两种模式
set TGAI_SPV_DIR=D:\tgai_build
_gb.exe                    :: 默认（应全部返回 0）
set TGAI_USE_GPU=1
_gb.exe                    :: 启用（应全部走 GPU 且数值一致）
```
