# ★ 逐算子 GPU 桥接：三版实测 + 正确架构设计

**日期**：2026-10-10
**结论**：**逐算子桥接已止损（性能恢复基线）；正确架构是"整前向常驻设备"**

---

## 一、三版实测对照（真实 V2.7 模型，80 tokens，temp=0）

| 版本 | 关键改动 | CPU | GPU 桥 | 变化 | 输出一致 |
|---|---|---|---|---|---|
| **v1** | 每次 alloc + 传输 | 10.70 tok/s | 4.00 tok/s | **−62.6%** | ✅ 逐字相同 |
| **v2** | 缓冲池 + 权重常驻 | 11.20 tok/s | 5.80 tok/s | **−48.2%** | ✅ 逐字相同 |
| **v3** | **+ 1 MB 最小数据量门槛** | 11.20 tok/s | 10.90 tok/s | **−2.7%** | ✅ 逐字相同 |

**v3 的 −2.7% 在测量噪声范围内 ⇒ 已恢复到 CPU 基线。**

### 三版的意义

```
v1 → v2：证明"缓冲池 + 权重常驻"确实有效（改善 14.4 个百分点）
v2 → v3：证明"门槛"是对的 —— 挡下小算子后，桥接开销归零
v3 的结论： ✅ 可以安全保留在代码里（默认不启用，启用也不掉性能）
            ❌ 但也没有任何加速（因为门槛挡下了所有算子）
```

## 二、为什么逐算子桥接注定失败（数量级分析）

```
单次 RMSNorm（TGAI V2.7）:
  输入: 8 × 1024 × 4 = 32 KB
  计算: 16 KFLOP ÷ 370 GFLOP/s = 0.043 µs     ← 43 纳秒

单次 Vulkan dispatch + 同步（实测经验值）:
  vkUpdateDescriptorSets       10~50 µs
  vkResetCommandBuffer +
  vkBeginCommandBuffer          5~20 µs
  vkCmdBindPipeline/Desc        5~20 µs
  vkEndCommandBuffer            2~5 µs
  vkQueueSubmit                20~100 µs
  vkWaitForFences（同步等待）   50~300 µs    ← 大头
  ------------------------------------------
  合计                        100~500 µs

比值: 100 µs / 0.043 µs = 2325 倍
⇒ 即使 GPU 计算快 100 倍，净结果仍是慢 23 倍
```

**⇒ 不是优化不够，是用错了层次。**

---

## 三、值得走 GPU 的判据（经验公式）

```
值得走 GPU ⟺ 计算时间 > 10 × dispatch 开销
核显 370 GFLOP/s、dispatch 100 µs
⇒ 需要 ≥ 3.7 MFLOP

实测各算子:
  RMSNorm (16 KFLOP)        → 0.04 µs    ❌ 差 25000 倍
  专家矩阵乘 (8.4 MFLOP)     → 23 µs      ❌ 差 4 倍
  Attention (seq=512)       → 27 µs      ❌ 差 37 倍
  ★ 整个前向 (28 层, 2.4 GFLOP) → 6.5 ms  ✅ 划算！
```

**⇒ 只有"整个前向"这一个粒度才划算。**（这正是 llama.cpp 的做法）

## 四、正确架构设计（方案 B，需 5~8 天）

### 4.1 核心思路

```
❌ 逐算子：Python/C 引擎 → N 次 GPU 往返（N × 100 µs）
✅ 整前向：一次提交包含全部 28 层的算子序列
          中间张量全部常驻设备内存，一次都不回主机
```

### 4.2 显存预算（已实测可行）

```
TGAI V2.7 权重（BF16）:  5.64 GB
核显可用"显存"（实测）:  7.25 GB
------------------------------------------------
权重全部常驻后剩余:      1.61 GB   给激活 + KV cache + 工作区

激活（seq=1）:  ~几 MB        ✅ 够
KV cache:      8192 × 16 × 64 × 2 × 4 = 134 MB（BF16 减半）
工作区:        ~100 MB        ✅ 够
------------------------------------------------
⇒ ★ 技术上可行，余量充足
```

### 4.3 需要新增的模块

| # | 模块 | 说明 | 已有基础 |
|---|---|---|---|
| 1 | **权重常驻管理器** | 启动时把全部权重上传设备（5.64 GB）| 桥接层的 wcache 可扩展 |
| 2 | **设备侧张量表** | 每层的中间张量分配一次，全程复用 | 桥接层的 pool 可扩展 |
| 3 | **命令缓冲录制器** | 把 28 层的算子序列录进一个 command buffer | 需要新写 |
| 4 | **最终 logits 回读** | 只有输出一次 download | 已有 |
| 5 | **备用回退** | 显存不足时自动回落 CPU | 已有（caps 判定）|

### 4.4 预期收益（推算，需实测验证）

```
当前 CPU:  11.2 tok/s（单线程 AVX2 实测）
核显矩阵乘: 14.2 GFLOP/s（seq=1 实测）

V2.7 单 token 计算量: ~2.4 GFLOP（28 层 × MoE 2 专家）
⇒ 纯计算时间: 2.4e9 / 14.2e9 = 169 ms     ← 单token！
⇒ 等效 5.9 tok/s

⚠️ 推算结论：核显矩阵乘速度（14.2 GFLOP/s）反而【低于】CPU 的
   有效算力（11.2 tok/s × 2.4 GFLOP = 26.9 GFLOP/s）
⇒ ★ 方案 B 即使实现完美，也可能仍然慢于 CPU！

原因：seq=1 时矩阵乘是【纯带宽受限】——
      必须读完整权重（5.64 GB）但只算 2.4 GFLOP
      核显带宽实测 ~7 GB/s ⇒ 5.64/7 = 806 ms/token  ⇒ 1.2 tok/s !
```

### 4.5 ⚠️ 所以我要修正上一轮的判断

**上一轮我说"方案 B 可能真正加速"—— 现在重新算账，结论更悲观**：

| 路径 | 单 token 时间 | 等效速度 |
|---|---|---|
| **CPU（实测）** | 89 ms | **11.2 tok/s** |
| GPU 常驻（按带宽算）| 806 ms | **1.2 tok/s** |
| GPU 常驻（按算力算）| 169 ms | 5.9 tok/s |
| **⇒ GPU 取两者较大值** | **806 ms** | **1.2 tok/s** |

**⇒ 核显跑 V2.7 的瓶颈是【内存带宽】，而它与 CPU 共享同一条总线。**
**即使架构完美，GPU 也快不过 CPU —— 因为数据要从同一条内存里读出来。**

## 五、诚实结论（修正后的判断）

| 问题 | 答案 |
|---|---|
| 逐算子桥接能用吗？ | ✅ 能用，输出完全正确 |
| 性能？ | v3 已恢复到基线（−2.7%）|
| **整前向常驻能加速吗？** | ❌ **推算不能** —— 核显与 CPU 共享内存总线，带宽是共同瓶颈 |
| 那核显的 GPU 加速有意义吗？ | ⚠️ **只在特定场景**：seq 大（prefill）时算力才成为瓶颈 |
| 什么时候有意义？ | ✅ **prefill / 批量**（我实测 seq=8 时 164 GFLOP/s，比 CPU 快 58×）|
| 我做的 7 个内核白费了吗？ | ❌ 没有 —— 在 **prefill** 场景下立刻有价值 |

### ★ 修正后的方向：GPU 只用于 prefill，decode 用 CPU

```
decode（seq=1）: CPU 更快（11.2 tok/s vs GPU 推算 1.2 tok/s）
prefill（seq≥8）: GPU 更快（164 GFLOP/s vs CPU 2.8 GFLOP/s，58×）

⇒ 混合策略：
    prefill 阶段（处理 prompt）→ 走 GPU
    decode 阶段（逐 token 生成）→ 走 CPU
```

**这在 llama.cpp 里叫 `--no-kv-offload` 类策略，是真实存在的优化手段。**
