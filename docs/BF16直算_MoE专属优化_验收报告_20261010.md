# ★ BF16 直算（MoE 专属优化）—— 实施与验收报告

**日期**：2026-10-10
**结论**：**内存省 32~60%、速度 2.26×、数值逐位完全相同。**

---

## 一、为什么要做（用户提出的问题）

> 「为什么我们不直接用 BF16 做矩阵乘？虽然小模型没事，但是我们以后模型肯定越来越大啊！
> 3B，5B，7B……30B！那么为什么 llama.cpp 在这个情况下加载速度也快？」

### 实测根因

| 项 | TGAI GO（改前）| llama.cpp |
|---|---|---|
| BF16 权重存放 | **懒解码成 FP32 缓存** | **保持 2 字节（mmap 就地）** |
| 矩阵乘 | FP32 内核 | `ggml_vec_dot_bf16` **原生 BF16 内核** |
| 加载 | 分配缓存数组 | **mmap 只做映射，不读数据** |

**代码依据**（llama.cpp 实测查证）：
```
ggml/src/ggml-cpu/ggml-cpu.c
  L396:  .vec_dot = (ggml_vec_dot_t) ggml_vec_dot_bf16      ← ★ 原生 BF16 点积
ggml/src/ggml.c
  L885:  [GGML_TYPE_BF16] = { .blck_size=1, .type_size=2,    ← 恒 2 字节
                              .to_float = ggml_bf16_to_fp32_row }
  L458:  注释："it just left shifts"                          ← 转换 = 左移 16 位
```

### 容量账（这是关键）

| 模型 | 文件(BF16) | TGAI GO 旧方案(FP32) | BF16 直算 |
|---|---|---|---|
| V2.7 (0.86B) | 5.64 GB | **11.3 GB** | 5.64 GB |
| 3B | 6 GB | **12 GB** | 6 GB |
| **V3 (7B)** | **14 GB** | **28 GB** ❌ | **14 GB** ✅ |
| 30B | 60 GB | **120 GB** ❌ | 60 GB ✅ |

**⇒ 30B 在旧方案下根本不可能；V3 的 7B 在 32 GB 机器上也不可行。**

## 二、TGAI 的 MoE 架构专属分析（为什么这对我们特别重要）

**实测 V2.7 权重构成**（`D:\tgai_gguf_work\v27_merged_bf16.TG`，982 条目）：

```
权重数据总计: 5.64 GB
├─ ★ MoE 专家 FFN (w1/w2/w3):  5.25 GB  (93.1%)  728 条目
├─   注意力 q/k/v/out:         0.22 GB  ( 3.9%)  112 条目
└─   其余(norm/embed):         0.17 GB  ( 3.1%)   58 条目

单个专家 (w1+w2+w3): 24.00 MB
每层激活 2 专家:     48.00 MB
每 token 读专家权重: 1.31 GB（28 层 × 2 专家 × 24 MB）
```

**⇒ 93.1% 的字节在 MoE 专家 ⇒ BF16 直算的收益 93.1% 来自 MoE。**

**这与之前所有 MoE 专属工作的结论一致**：
| 已做 | 依据 |
|---|---|
| QB 路由偏置 | TGAI 2.7 的 `moe_balance='both'`（quantile balancing）**专有** |
| 专家布局核实 | 实测 `.TG` 里 `experts.{e}.w1/w2/w3` **顺序连续** ⇒ 不需 packing |
| w3 多行内核 | 针对 TGAI 的两种专家形状实测差异（`[896,3584]` 1.77x vs `[3584,896]` 1.10x）|
| **BF16 直算** | **93.1% 权重在 MoE 专家** |

## 三、实现（6 步，全部可回退）

| 步 | 改动 | 位置 |
|---|---|---|
| 1 | `bf16_dot` 内核（AVX2 寄存器内解包 + 标量回退） | `tgai_engine.c` |
| 2 | `use_bf16_direct` 开关 + `TG_EXPORT` 接口 + 环境变量 | 同上 |
| 3 | `cached_bf16_raw[]`（与 `cached_q4_raw` 并列，零拷贝直指 mmap） | `preload_weights` |
| 4 | `MatmulArgs.bf16` + 两个 worker 的 BF16 分支 | 同上 |
| 5 | `MoeMMArgs.b1/b2/b3` + BF16 版 MoE worker | 同上 |
| 6 | `RESOLVE_W_BF16` 宏（8 个大权重）+ 4 处前向分发 | `init_block_cache` / `transformer_block` |

### 内核原理（llama.cpp 同款技巧）

```c
/* bf16 → fp32 就是【左移 16 位】（ggml 原话："it just left shifts"） */
__m128i w16 = _mm_loadu_si128((const __m128i*)(w + i));      // 8 个 bf16
__m256i w32 = _mm256_slli_epi32(_mm256_cvtepu16_epi32(w16), 16);  // 解包成 fp32
acc = _mm256_fmadd_ps(_mm256_loadu_ps(x + i),
                      _mm256_castsi256_ps(w32), acc);
```

### 分发优先级（与既有 Q4 判空逻辑同构 ⇒ 零回归风险）

```
① q4_expert_w1[e] 非空   → Q4_0 直算（既有）
② bf16_expert_w1[e] 非空 → ★ BF16 直算（新，V2.7 主路径）
③ 否则                   → FP32 懒解码（老行为，完全不变）
```

**向后兼容**：`use_bf16_direct` 默认 1，但**只对 `dtype == TG_DTYPE_BF16` 生效** ⇒
老模型（Q4_0/FP16/FP32）**完全不受影响**。

### 汇总

| 指标 | 旧（FP32 展开）| **新（BF16 直算）** | 改善 |
|---|---|---|---|
| prefill | 5.84 s | **3.09 s** | **1.89×** |
| decode | 5.7 tok/s | **12.9 tok/s** | **2.26×** |
| RSS（稳态）| 5295 MB | **3574 MB** | **−32%** |
| **峰值 RSS** | **8942 MB** | **3574 MB** | **−60%** |
| logits | — | — | **逐位相同** |

**峰值内存是关键**：旧的 8942 MB 会让 8 GB 设备直接失败；新的 3574 MB 可跑。

## 五、为什么速度反而快了（机理）

**因为本机实测是带宽受限**（之前的实测结论）：
```
每 token 读 MoE 专家权重 206.7 MB（Q4 模型）/ 1.31 GB（V2.7 BF16）
实测有效带宽 3.03 GB/s，而 4 线程可用 8.60 GB/s ⇒ 只发挥 35%
单核读带宽仅 2.54 GB/s ⇒ 内存【延迟】受限
```

**⇒ 字节数减半直接换吞吐。**这与 A 的 vocab hash 优化同源（都是缩小工作集）。

## 七、已知限制与后续

| 项 | 状态 |
|---|---|
| AVX2 路径 | ✅ 已实现并验证 |
| 标量回退（嵌入式/无 AVX2）| ✅ 已实现（未在硬件验证）|
| ARM NEON 版 | ⬜ 未做（ARM 上是 bf16→fp32 用 `vcvt` 即可，工作量小）|
| 与 `use_q4_direct` 组合 | ✅ Q4 优先，二者互斥不冲突 |
| Q4_0 的 BF16 化 | ⬜ Q4_0 已省内存，无需再转 |

### ★ 对 V3 的意义

V3 是 **7B MoE（8 专家 top-2）+ 64K 上下文 + 96K 词表**：
- 纯权重：14 GB（BF16）→ 旧方案 28 GB ❌ → **直算 14 GB ✅**
- 加上 KV cache（64K 上下文）+ 工作区，**32 GB 机器可跑**（旧方案不可能）
- 加上本轮已有的 **vocab hash**（96K 词表编码）⇒ V3 的两个内存热点都已解决
