# ★ 内存规划器 —— 按模型大小自动分配内存

**日期**：2026-10-10
**目的**：让推理引擎**自己算出该分配多少内存**（而不是给用户一个滑块去猜）

---

## 一、为什么"自动算"比"滑块"好

```
PCL 那个滑块：用户猜 → 猜大了浪费，猜小了 OOM

推理引擎有足够信息【算】：
  · 模型头部写着 d_model / n_layers / n_experts / max_seq_len / n_kv_heads
  · 权重字节数可以从权重表精确求和
  · 可用内存可以查 GlobalMemoryStatusEx
⇒ 算得出来就该自动算，用户只在"快 vs 省"之间选策略
```

---

## 二、★ 规划器跑出来的第一个重大发现

### 用真实 V2.7 参数（未修正版）

```
权重      5.59 GB
KV cache  1.75 GB
工作区    1.47 GB
激活缓存  11.17 GB    ← ★★★ 元凶
合计      19.98 GB    ⇒ 16 GB 机器【装不下】！
```

**这解释了引擎早期的一个真实问题**：
```
引擎实测（我这一 session 早先的记录）:
  未开 BF16 直算: 峰值 RSS 8942 MB   ← 11 GB 需求的来源
  开启 BF16 直算: 峰值 RSS 3574 MB   ← 实际默认状态
```

**⇒ 激活缓存（懒解码成 FP32）是内存杀手，BF16 直算把它消掉了。**

### 修正后的正确账

```
权重      5.59 GB
KV cache  1.75 GB
工作区    1.47 GB
激活缓存  0.00 GB   ← BF16 直算（引擎默认开启）
合计      8.80 GB   ⇒ FEASIBLE ✅
```

## 三、修正的两个错误（都是我第一版写错的）

| # | 错误 | 后果 | 修正 |
|---|---|---|---|
| **1** | 激活缓存按"权重元素数 × 4 字节"算（11.17 GB）| **误报内存不足** | 按 BF16 直算是否开启区分：开启 ⇒ 0；关闭 ⇒ weight_bytes × 2 |
| **2** | 安全余量取 `max(20%, 1.5GB)` = 3.08 GB | **预算被压到 4.55 GB < 权重 5.59 GB ⇒ 误报 OOM** | 分档：<8GB 留 25%；8~16GB 留 20%；>16GB 留 2.5GB；上限 2.5GB 下限 512MB |

**教训**：内存估算的每一项都要有"实测依据"，不能凭直觉设系数。

## 四、规划器的设计

### 四类需求

| 项 | 算法 | 实测校验 |
|---|---|---|
| **权重** | 直接用 .TG 权重表求和（最准）| V2.7 = 5.59 GB（文件 5.64 GB 减头部）|
| **KV cache** | `2 × L × max_seq × n_kv_heads × head_dim × 4` | 28×8192×16×64×2×4 = 1.75 GB |
| **工作区** | `seq × (d×7 + d_ff×2 + vocab + n_experts) × 4` | 按 4096 算 = 1.47 GB |
| **激活缓存** | BF16 直算开 ⇒ 0；关 ⇒ `weight_bytes × 2` | 实测峰值 RSS 印证 |

### 三种策略

| 策略 | 激活缓存 | 预缓存权重 | 线程数 | 适用 |
|---|---|---|---|---|
| **conservative** | 不留 | 否 | 一半 | 内存紧张（同时开浏览器等）|
| **balanced**（默认）| 留一半 | 够就留 | 3/4 | 日常 |
| **performance** | 全留 | 是 | 全部 | 只跑模型 |

### 决策输出（写回引擎的参数）

```
work_seq      : 708 tokens   ← 替代硬编码的 64（L2107）
kv_max_seq    : 4096 位置    ← 按预算裁剪
cache_all_weights : 是/否
nthreads      : 8 / 12 / 16  ← 按策略
slack_bytes   : 剩余余量（负数 = 不可行）
```

## 六、现状与下一步

### 已完成

```
src/tgai_memplan.h / .c     内存规划器（独立模块，已编译验证）
tests/demo_memplan.c        演示程序（用真实 V2.7 参数）
```

### ⚠️ 还没做：接入引擎

**接线点已经找好**：

| 位置 | 现状 | 应改为 |
|---|---|---|
| `L2107` | `m->max_work_seq = 64;` **硬编码** | `plan.work_seq` |
| `L2202` `ensure_work` | 不够就 `realloc(seq*2)` ⇒ 运行中抖动 | 按 plan 一次分配够 |
| `tg_load` 之后 | 无内存报告 | 调 `tg_mem_plan` + `tg_mem_plan_print` |
| `tg_set_nthreads` | CLI 参数 | 可用 `plan.nthreads` 作建议值 |

**接线收益**：
```
① 消除运行中 realloc 抖动（现在是 64 → 128 → 256 → ... 反复重分配）
② 启动就告诉用户"为什么慢/为什么可能失败"
③ 内存紧张时自动降级（而不是 OOM）
```

**预估工作量**：1 天（含回归测试）
