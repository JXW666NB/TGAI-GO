## 三、★ 为什么 GPU 加速在本机不可行（量化依据）

### 3.1 逐算子桥接：dispatch 开销碾压计算量

```
RMSNorm 计算: 16 KFLOP ÷ 370 GFLOP/s = 0.043 µs
Vulkan dispatch + 同步:                 100~500 µs
比值: 2325 倍

⇒ 即使 GPU 计算快 100 倍，净值仍慢 23 倍
```

**实测三版**（真实 V2.7，80 tokens）：

| 版本 | 改动 | GPU vs CPU |
|---|---|---|
| v1 | 每次 alloc + 传输 | **−62.6%** |
| v2 | 缓冲池 + 权重常驻 | **−48.2%** |
| v3 | + 1 MB 门槛 | **−2.7%**（噪声内）|
| v6 | 门槛 8 GB（全挡）| **0.0%**（逐字相同）|

### 3.2 整前向常驻：带宽是共同瓶颈

```
核显跑 V2.7 单 token:
  必须读完整权重 5.64 GB
  核显带宽实测 ~7 GB/s
  ⇒ 806 ms/token = 1.2 tok/s

CPU 实测: 11.0 tok/s（91 ms/token）

⇒ 慢 9 倍。原因：核显与 CPU 【共享同一条内存总线】
   "用内存当显存"的代价就是"和 CPU 抢总线"
```

### 3.3 唯一有实测支撑的加速场景：prefill

```
decode（seq=1）: CPU 更快（11.0 tok/s vs GPU 推算 1.2 tok/s）
prefill（seq≥8）: GPU 更快 —— 实测 164 GFLOP/s vs CPU 2.8 GFLOP/s = 【58×】
```

## 四、★★ 本轮发现的一个未修复 bug（诚实报告）

**mm_bf16 桥接输出乱码**：

```
实测：加入 mm_bf16 接线后（门槛 1 MB）
  GPU 输出: "听据此展，有病"   ❌
  token 数: 32（正常 40+）     ❌

门槛提到 1024 MB（挡住 mm_bf16）后：
  GPU 输出: 与 CPU 逐字相同     ✅

⇒ 确认是 mm_bf16 桥接的 bug
```

**我做的排查**：
1. ✅ 发现并修正了**布局不匹配**：引擎用 `[seq][k]`/`[seq][n]`，
   我的内核用 `[k][seq]`/`[n][seq]` ⇒ 写了新版内核 `mm_bf16_engine.comp`
2. ❌ **修正后仍然乱码** ⇒ 还有别的 bug（未找到）

**未找到的可能原因**（供后续排查）：
- 权重打包的缓存 key 冲突（我用 `wbf` 指针 + `pkbytes` 作 key，
  但同一指针可能对应不同 n/k 组合）
- split-K 的 `split` 值选择与部分和缓冲大小不匹配
- `tg_vk_mm_reduce_cpu` 的索引约定与内核的 `[split][seq][n]` 布局不一致

⚠️ **注意**：这个 bug 在"门槛 8 GB"的默认配置下**不会被触发**，
所以当前状态是安全的。**但修复前不要调低 `TG_GPU_MIN_BYTES`。**
