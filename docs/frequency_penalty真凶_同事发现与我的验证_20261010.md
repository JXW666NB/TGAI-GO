## 一、同事的发现（原文要点）

| 实验 | 结果 |
|---|---|
| **PyTorch 前向 vs llama.cpp 贪心**（同一 77 token prompt）| **几乎逐字相同** ⇒ **前向是忠实的，转换没问题** |
| 贪心 vs temp 0.3 | 贪心全对（含 108 token 长 prompt）⇒ 不是温度 |
| 参数矩阵 | freq **0.00 / 0.25 / 0.40 ✅** ｜ 0.60 ⚠️ 不稳定 ｜ **1.20 ❌ 乱码** |
| repeat_penalty 隔离 | rep 1.25 配低 freq **完全安全** ⇒ 与 rep 无关 |
| 去掉 DRY | 照样崩 ⇒ **DRY 不是元凶** |

### 机理（关键）
> llama.cpp 的 `frequency_penalty` 是 **`logit -= 出现次数 × freq`** ——
> **惩罚随上下文长度无限累积**，把"的/了/情绪"这类高频词越压越狠，
> **模型被推出训练分布**。所以**上下文越长越崩**。
> 云端 Python 引擎用的是 **0.25**，所以云端没事。

### 同事的改动
| 文件 | 改动 |
|---|---|
| `index.html` | 默认 `frequency_penalty` **1.2 → 0.25**；6 个预设全部同步；提示文案改成"不能超过 0.4" |
| `server.py` | 兜底默认 **1.3 → 0.25** |

**他的自省**：上一轮"输出怪怪的"时只抓到 prompt 格式 bug 就收场，没做严格前向对照；
这次补上后结论才站得住 —— **而且结论恰好是"转换没问题"，是参数问题**。

## 二、TGAI GO 侧的情况：实现同构，但有一处关键差异

### 2.1 实现对比（我的代码逐行核对）

```python
# tgai_chat.py L233-241 —— 与 llama.cpp 完全同构
if fp != 0.0:
    cnt = {}
    for tid in hist:            # hist = recent[-repeat_last_n:]
        cnt[tid] = cnt.get(tid, 0) + 1
    for tid, c in cnt.items():
        if 0 <= tid < logits.size:
            logits[tid] -= fp * c        # ← logit -= 出现次数 × freq（同 llama.cpp）
```

### 2.2 ★ 关键差异：**我的惩罚窗口有界**

```python
n = int(p.get('repeat_last_n', 64) or 0)
hist = recent[-n:]          # ← 只取最后 64 个 token
```

**llama.cpp 默认 `repeat_last_n = 64`，`frequency_penalty = 0.0`（关闭）**。
而同事的面板把 freq 设成 **1.2**，窗口内每个重复 token 每次减 1.2 —— 累积极快。

**⇒ TGAI GO 的默认 `frequency_penalty = 0.35` 配 `repeat_last_n = 64`，理论上安全得多。**

### 2.3 但我**实测验证**了（不瞎猜）

`tools/sweep_freq_penalty.py`，模型 = `v27_bf16.TG`（V2.7 基座，逐位无损），
纯贪心 + 与 `tgai_chat.py` 完全同源的惩罚实现：

| freq | EOS 率 | 前 12 token | 文本 |
|---|---|---|---|
| **0.00** | 30% | `8 8 8 8 8 8 …` | `\n\n\n\n\n\n\n\n\n…` |
| **0.25** | 13% | `8 8 8 8 8 8 …` | `\n\n\n\n\n\n。\n\n<EOS>。\n。。` |
| **0.35** | 10% | `8 8 8 8 8 8 …` | `\n\n\n\n\n\n。<EOS><EOS>，\n。。` |
| 0.40 | 17% | `8 8 8 8 8 8 …` | `\n\n\n\n\n\n。\n\n。<EOS><EOS>，。` |
| 0.60 | 10% | `8 8 8 8 8 24 3` | `\n\n\n\n/<EOS>。\n\n白<EOS>，。\n\n不出` |
| 0.80 | 7% | `8 8 8 11 24 11` | `\n\n\n"/"""。<EOS>//。\n\n在一个，如一个，不` |
| **1.20** | 3% | `8 11 11 11 11 496` | **`\n""""。<EOS>了//{)。\n##/,在：不是，如有。或`** |
| **2.00** | 3% | `8 11 24 11 496 18` | **`\n"/"。)了{<EOS>一个\|等多\(，或如不少于.大对、精`** |

### 2.4 结论

**① 同事的发现对 TGAI GO 同样成立**：
`freq ≥ 1.2` 出现典型的**符号噪声**（`/"""`、`{)。`、`##/,`、`\(`）——
这就是"被推出训练分布"的特征。**我们的默认 0.35 安全，但采纳他的建议降到 0.25~0.30 更稳。**

**② 但 freq=0 时也复读 `\n` ⇒ TGAI GO 有更深的独立问题，与惩罚参数无关。**

证据：
```
freq=0.00（零惩罚）→ 纯贪心 → '\n\n\n\n\n\n\n\n\n\n\n\n\n\n\n\n'
```
而 `repeat_penalty` 单独扫描（freq=0）也全是 `\n` 复读：
```
rp=1.00 distinct=2   '\n\n\n\n\n\n\n\n\n\n\n\n\n\n\n\n<EOS><EOS'
rp=1.50 distinct=4   '\n\n\n\n\n\n\n\n\n。\n\n<EOS>\n\n，\n\n\n\n\n'
```

**③ 反向证据**：freq 越高 distinct 越多（2 → 11），
说明**惩罚在"帮忙"制造多样性** —— 这是**分布本身已经不对**的典型特征，而不是参数问题。

### 行动 4 的排查方向（TGAI GO 专属）

| # | 假设 | 依据 | 验证方法 |
|---|---|---|---|
| **1** | **MoE 路由的 QB 偏置方向/符号错** | V2.7 用 aux-loss-free 均衡，偏置加错会系统性偏移专家选择 | 对比"加偏置 / 不加 / 减偏置"三档的 logits 分布 |
| 2 | 注意力实现细节与训练不一致 | 可能性中等 | 逐层 dump 与 PyTorch 对比 |
| 3 | RoPE 应用方式（cos/sin 布局）| 若错，长上下文会退化，但短 prompt 也应可见 | 对比位置 0 与位置 k 的注意力 |
| 4 | prompt 的 `<回答>` 未触发"该说话"状态 | 同事侧同一 prompt 能出字 | 换更多 prompt 格式对比 |
| 5 | 权重读取的转置/形状误读 | Q4_0 版崩得更厉害（EOS logit 4.3→14.0）说明对数值敏感 | 挑一个权重与 PyTorch 逐元素对比 |

**★ 最优先**：假设 1（QB 偏置）—— 因为：
- 它是 V2.7 独有的机制（老模型没有）
- 我实现它时**没有真实 V2.7 模型可验证**（当时只能造测试文件）
- 偏置是**加到 router logits 上再 top-k** ⇒ 加错会让路由选错专家 ⇒ 直接破坏 FFN 输出
