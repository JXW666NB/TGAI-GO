# GPU 接线现状与 N 卡测试待办（2026-10-11）

> **这份文档的目的**：把 GPU 加速这条线的**现状、已做的改动、待验证项**固化下来，
> 让"换一台带 N 卡独显的机器（或远程 SSH 过去）"时能立刻接上，不靠记忆。
>
> **一句话现状**：引擎侧的"接线缝"、Vulkan 分派层、独显+显存门槛**都已实现并验证**，
> 但**从未在真实独立显卡上端到端跑过** —— 本机只有 AMD 核显。

---

## 一、为什么要做这件事（问题起因）

用户诉求原文：

> "有什么办法解决吗？Vulkan 后端 / 这对项目兼容性有很大影响"
> "根据人家官方的可复现的 Vulkan 构建路径去尝试 / 我们搞不到，但是也要尝试"
> "如果可以允许用户用一条函数强制继续编译和启用GPU"
> "由于本机的核显，和CPU抢内存通道因此慢是肯定的
>  但是检测到独立显卡就接线（但是门槛是显存要装得下所加载的模型）"

**背景事实**：项目里 `tgai_vulkan.c`（603 行内核）、`third_party/vulkan/volk.c`
（4284 行官方 loader + 头文件）、`cuda/tgai_cuda.cu`（7 个 `__global__` 内核）
**都是完整实现**，但 `tgai_engine.c` **从未调用**任何 GPU 后端 ——
`tgai_backend.c/h` 是孤立文件（全项目没有 `.c` include 它，
`TG_BE_HAS_VULKAN` 无人 define），引擎只挂了 `tg_npu_matmul` 一个钩子。

**⇒ 缺的不是实现，是一条电线。**

## 二、已完成（可复现，都有实测数据）

### 2.1 引擎侧"接线缝"（提交 `88f9abf`）

`src/tgai_engine.c` 新增三个钩子，语义与既有 `tg_npu_matmul` **完全一致**：

```c
int  tg_gpu_matmul(float* out, const float* x, const float* w, int seq, int k, int n);
/* 返回 1 = 已接管计算（out 已填好）；返回 0 = 不可用/不支持，调用方走 CPU */
int  tg_gpu_backend_init(void);        /* 返回 1 = 就绪 */
void tg_gpu_backend_shutdown(void);
```

调用点（`_matmul_impl` 内，紧跟 NPU 钩子之后，同样只在 `!q4` 的 FP32/BF16 路径）：

```c
if (!q4 && tg_npu_matmul(out, x, w, seq, k, n)) return;
if (!q4 && tg_gpu_matmul(out, x, w, seq, k, n)) return;   /* 新增 */
```

**默认全是空桩（返回 0）⇒ 不接 GPU 的构建行为与以前 100% 一致。**

> ★ 踩坑：本项目靠 `TG_EXPORT`（`__declspec(dllexport)`）在**头文件**里声明才导出符号。
> 第一版只改了 `.c` 没改 `.h`，`dumpbin /exports` 查不到 `tg_gpu_matmul`。

### 2.2 Vulkan 分派层（`src/tgai_gpu_dispatch.c`，740 行）

编译开关：`-DTG_LINK_GPU_SEPARATE -DTG_GPU_VULKAN`
（必须**同时**编译 `src/tgai_vulkan.c` + `src/tgai_vk_kernels.c` +
`third_party/vulkan/volk.c`，否则 LNK2019）

**实测数据**（`tests/test_gpu_dispatch.c`，本机 AMD 核显）：

| 项目 | 结果 |
|---|---|
| 数值误差 4096×1024 | 相对 **3.706e-04**（要求 <1e-2）|
| FP64 仲裁 | GPU 相对真值最大绝对偏差 **2.2e-06** |
| 权重缓存 | 同权重第二次调用命中 +1、miss +0；命中后 1.0~2.4 ms |
| 退出码 | 0，全部 PASS |

> ★ 一个必须记录的坑：4096×1024 形状里有 **1/4096** 个元素相对误差 1.18e-2 略超 1e-2。
> 该元素 `y_f64=9.8e-05`（大数相消出来的 ≈0，参与求和的单项量级 ~1.0），
> GPU 绝对误差只有 **8.3e-07**，CPU 自己也有 3.4e-07。
> **不是内核 bug**，是相对误差指标在相消元素上的固有放大。
> 判据已改为"相对 或 绝对（<1e-4×rms）"并加 FP64 仲裁。

> ★ 澄清历史疑点：老的 `tgai_gpu_bridge.c` 注释说 mm_bf16 "有正确性 bug、输出乱码"。
> 现在证明**内核是对的**；当年乱码根因是**没转置 x**
> （内核读 `x[k][seq]` 步长=seq，而引擎给的是 `[seq][k]`）。本实现已做转置。

### 2.3 核显 vs 多线程 CPU 的实测交叉点（决定性数据）

| 形状 | CPU 多线程 | GPU | 结果 |
|---|---|---|---|
| 4096×1024 seq=1 | 0.65 ms | 0.95 ms | **0.68×（CPU 胜）**|
| 1024×1024 seq=16 | 0.31 ms（107 GFLOP/s）| 0.97 ms | **0.32×（CPU 胜）**|
| 8192×4096 seq=4 | 6.72 ms | 4.45 ms | 1.51×（GPU 胜）|

**⇒ 本机核显交叉点约 250~270 MFLOP。**
引擎的真实对手是**多线程** CPU（107 GFLOP/s），不是单线程（14.6）。

**核显与 CPU 共享内存控制器（UMA）⇒ 一起跑只是互相抢带宽。**
这与用户的判断一致。

### 2.4 独显接线 + 显存门槛（提交 `4ddc762`）

设计（已写进 `tgai_gpu_dispatch.c` 注释）：

```
核显（device_type=1 / is_uma=1）
    → 保持 FLOP 门槛（默认 3e8，基本不用 GPU）
      ：与 CPU 抢内存通道，小算子必输

独显（device_type=2）且有独立显存
    → 唯一硬门槛 = 显存装不装得下模型
        显存 ≥ 模型 × 1.25（TG_GPU_VRAM_HEADROOM 可调，KV/激活/驱动余量）
            ⇒ 全量走 GPU（权重常驻显存，每 token 只传激活）
        装不下
            ⇒ 回落 CPU（每 token 要重传 1.7 GB 权重，必然更慢）
```

实现要点：

- **设备选择复用 `tg_vk_init(-1)`**：它**本来就优先挑独显**
  （`VK_PHYSICAL_DEVICE_TYPE_DISCRETE_GPU`），**无需改**。
- 新增模块状态：`is_discrete` / `model_fits` / `vram_bytes` / `model_bytes`。
- `gd_worth_gpu()` 加**独显直通**：`is_discrete && model_fits ⇒ return 1`
  （只保留 workgroup 数量等硬结构限制）。
- 模型大小从哪来：dispatch **拿不到** `TGModel` 内部（不透明结构且不链接引擎）
  ⇒ 由 Python 侧传入环境变量 **`TG_GPU_MODEL_MB`**，`_engine.load()` 已自动设置。
- **测试后门**（命名带 FORCE，避免运维误用）：
  `TG_GPU_FORCE_DISCRETE=1` / `TG_GPU_FORCE_VRAM_MB=N`
  —— 用于在**没有独显的机器上验证独显分支的代码路径**。

**实测验证三个分支**（本机只有核显，用后门）：

```
① 真实核显                        → "就绪但非独显…核显 UMA，与 CPU 共享内存通道" ⇒ FLOP 门槛
② 后门独显 + 8000MB 显存 + 6000MB 模型 → "独立显卡…⇒ 全量走 GPU"               ✅
③ 后门独显 + 4000MB 显存 + 6000MB 模型 → "装不下模型 6000 MB（需 1.25x 余量）
                                        ⇒ 回落 CPU 门槛判定"                    ✅
④ 回归：默认门槛下小任务仍被挡住                                              ✅
```

## 三、⚠️ 关键踩坑记录（下次务必先读）

### 3.1 改了 `tgai_engine.c` 后必须同步刷新包内 DLL

```
必须复制：cpu\build\libtgai_engine.dll
      →   python\tgai_go\_native\libtgai_engine.dll
```

否则 Python 加载的是**包内旧 DLL**，新符号全部 `AttributeError`，
而 `_engine.py` 的 `except AttributeError` 会把它**吞掉**
⇒ 表现为 `gpu_info = None` **静默无输出**，极难排查。

**验证方法**：`dumpbin /exports python\tgai_go\_native\libtgai_engine.dll`

### 3.2 编译脚本路径含空格

`D:\tgai_nlp\TGAI GO` 有空格。Python 里 `['cmd','/c',script]` 会被 cmd 拆开：
```
'\vulkan' is not recognized as an internal or external command
'ist' is not recognized as an internal or external command
```
⇒ 必须把**带引号的整条命令**作为字符串传（`'cmd /c "%s"' % script`）。

### 3.3 `.bat` 文件必须纯 ASCII

cmd 按 **GBK** 读 `.bat`，UTF-8 中文注释会被当成命令执行
（实测报 `'运行' is not recognized`）。

### 3.4 不要用 `subprocess.run(capture_output=True)` 跑 bat

bat 若等待输入，`capture_output` 会一直等管道 EOF，**`timeout` 也不触发**
（进程还活着）⇒ 双向死锁。改用**重定向到文件**。

### 3.5 追加函数时注意 `if __name__ == '__main__':` 的位置

把 `force_gpu()`/`enable()` 追加到文件末尾 ⇒ 落在 `if __name__` **之后**
⇒ `main()` 执行时 `NameError: name 'force_gpu' is not defined`。
必须插在 `main()` 定义**之前**。

### 4.2 建议的准备

- 记录**显卡型号 / 显存大小 / 驱动版本 / Vulkan 版本**
- 记录 **CPU 型号与核数**（交叉点随 CPU 强弱变化很大）
- 准备 2~3 个不同大小的 `.TG`（验证显存门槛的边界）

### 4.3 已知缺口（诚实交代）

1. **CUDA 分派层未实现**。`cuda/tgai_cuda.cu` 有完整内核与 `tg_cuda_*` API，
   但**没有对应的 `tg_gpu_matmul` 实现**。目前 `TG_BACKEND=cuda` 是**诚实回落**。
   ⇒ N 卡机器上如果只想走 CUDA，**还需要再写一个 CUDA 版分派**
   （可照 `tgai_gpu_dispatch.c` 的结构，把 Vulkan 调用换成 cuBLAS）。
   **不过 Vulkan 在 N 卡上同样能跑**（Vulkan 是跨厂商的），
   所以最小可行方案是：**N 卡也先走 Vulkan 分派层**。
2. 门槛是**固定值**，未做 init 时微基准自动标定。
   理想做法：init 时跑一次微基准测出本机交叉点。
3. 门槛未考虑"引擎在 `seq < nthreads` 时走单线程"的情形
   （那种形状 GPU 本可赢却被挡 —— 偏保守，安全）。
4. 权重缓存 key 含尺寸，但**同尺寸不同张量复用同地址**理论上仍会读到陈旧数据，
   需 `tg_gpu_cache_clear()` 兜底。
5. **从未在真实独立显卡上端到端跑过整模型。**

### 4.4b ★ 下一步第一件事：把分派层链进引擎 DLL（当前状态下这是**未完成的**）

**已核实的现状**（`dumpbin /exports cpu\build\libtgai_engine.dll`）：

```
tg_gpu_matmul        ✅ 在    ← 但是【空桩版】（恒返回 0）
tg_gpu_backend_init  ✅ 在    ← 同上
tg_vk_probe          ❌ 不在  ← 关键证据：Vulkan 代码根本没链进来
tg_vk_init           ❌ 不在
```

原因：`cpu\build.ps1` **第 161 行写死了** `$src = ..\src\tgai_engine.c`，
只编这一个文件 ⇒ 拿到的是空桩。

**⇒ 分派层目前只编成了独立的 `test_dispatch.exe`（自检程序），
还没有和引擎连起来。**

要让引擎真正用上 Vulkan 分派，需要：

```
把 tgai_gpu_dispatch.c + tgai_vulkan.c + tgai_vk_kernels.c + volk.c
一起编进 libtgai_engine.dll，并加 -DTG_LINK_GPU_SEPARATE -DTG_GPU_VULKAN
```

**做这件事时必须注意**（否则会踩坑）：

1. **不能让 CPU 版失去兜底**。两种做法，必须选一种并想清楚：
   - 做法 A：产出**另一个** DLL（如 `libtgai_engine_vk.dll`），
     加载时用 `dll=` 显式指定 ⇒ CPU 版完全不受影响（**推荐**）
   - 做法 B：就地替换 `libtgai_engine.dll`
     ⇒ 必须先用 `TG_GPU_FORCE_DISCRETE=0` 等场景验证它仍能正常回落
2. **必须回归测试**：链进去之后 `TG_BACKEND=cpu` 下推理结果与现在**逐字一致**。
3. 打包时记得同步刷新 `python\tgai_go\_native\libtgai_engine.dll`
   （见 §3.1，这个坑很容易再踩）。

## 附：核显为什么慢（给下次的自己）

核显（iGPU）与 CPU **共享同一条内存总线与内存控制器**（UMA）。
两者同时跑，只是把同一份带宽切成两半，**没有净增益**。

这也解释了为什么"用内存当显存"只有**容量**意义、没有**速度**意义：
- 容量上可行：本机实测核显可用系统内存当显存（7.25 GB，真零拷贝）
- 速度上不行：多线程 CPU 107 GFLOP/s vs 核显 48 GFLOP/s

**独立显卡才有独立显存与独立内存控制器** —— 这才是"接线"的价值所在。
