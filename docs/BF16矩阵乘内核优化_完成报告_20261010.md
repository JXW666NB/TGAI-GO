# ★ BF16 矩阵乘内核优化 —— 完成报告

**日期**：2026-10-10
**结论**：**split-K 版内核验证正确，比朴素版快 1.73×（seq=1）/ 1.91×（seq=8）**

---

## 一、三版内核实测对比

**测试形状**：`[4096 x 1024] x [1024 x seq]`（V2.7 一个专家的 w1），权重 8 MB

### seq = 1（★ LLM 解码场景）

| 内核 | 耗时 | 吞吐 | 正确性 | 相对朴素版 |
|---|---|---|---|---|
| CPU AVX2（单线程）| 3.092 ms | 2.71 GFLOP/s | 基准 | — |
| GPU 朴素版 | 1.181 ms | 7.10 GFLOP/s | ✅ 0/4096 | 1.00× |
| GPU 行分块（LDS16/RPT4）| 0.563 ms | 14.90 GFLOP/s | ❌ 3923/4096 | **设计错误** |
| **GPU split-K（split=8）** | **0.592 ms** | **14.17 GFLOP/s** | ✅ **0/4096** | **1.99×** |
| GPU split-K（split=4）| 0.654 ms | 12.83 GFLOP/s | ✅ 0/4096 | 1.81× |

**⇒ 生产用 split=8。相对单线程 CPU 快 5.2×**

### seq = 8（prefill / 批量）

| 内核 | 耗时 | 吞吐 | 正确性 |
|---|---|---|---|
| CPU AVX2（单线程）| 23.720 ms | 2.83 GFLOP/s | 基准 |
| GPU 朴素版 | 1.225 ms | 54.76 GFLOP/s | ≈（1/32768 超 1%，是近零值）|
| **GPU split-K（split=4）** | **0.409 ms** | **164.08 GFLOP/s** | ≈（同上）|
| GPU split-K（split=8）| 0.660 ms | 101.68 GFLOP/s | ≈ |

**⇒ 生产用 split=4。相对单线程 CPU 快 58×**

## 二、★ 关键发现：优化方向选对了才有效

### ❌ 走了弯路：行分块 + RPT4（快 2.1× 但**结果全错**）

```
设计：16x16 线程，每线程算 4 行 × 1 列，权重/激活进共享内存
问题：LLM 解码时 seq=1
      ⇒ 列方向 16 个线程只有 1 个有效（利用率 6%）
      ⇒ 启动 64 工作组 × 256 线程 = 16384 线程，但只有 4096 个输出
      ⇒ 而且我的 sX 装载/读取索引不一致（ty 是 k 方向，tx 是列）
结果：err_max = 3.68e+03，3923/4096 不符
```

### ✅ 正确方向：split-K（专为小 seq 设计）

```
思路：把 K(=n_in) 切成 split 段，每段独立算部分和
      ⇒ 并行度 × split，每线程串行次数 ÷ split
      ⇒ 4096 输出 × 8 段 = 32768 个并行工作项（vs 4096）

实测 split 的最优点：
  seq=1  →  split=8   （4096*1/256=16 工作组 × 8 = 128 个）
  seq=8  →  split=4   （分太多反而因规约开销变慢）
```

**⚠️ 诚实说明**：行分块版**更快**（0.563 ms）但**结果是错的**。
我保留了这个失败版本在基准里作为对照 —— 它说明"快"不等于"对"。

## 三、GPU 上撞到的 4 个 GLSL 语法/语义坑

| # | 错误 | 根因 | 修法 |
|---|---|---|---|
| **1** | 进程崩 `0xC0000409` | 手写 Vulkan 结构体做 ABI 猜测 ⇒ 驱动越界写 | 用官方 `vulkan_core.h` |
| **2** | 结果全错（4080/4096）| **push constant std430 对齐**：12 字节 ≠ 16 的倍数 | `layout(offset=N)` + padding |
| **3** | 只有第 0 行对、y[4095]=0 | **分派维度写反**：`row=ID.y` 但 N_OUT 放进了 X 维 | `gx=列/16, gy=行/16` |
| **4** | 编译报 `atomicCompSwap` 找不到重载 | GLSL 450 core **没有 uint 重载**（那是 ES 3.1 特性）| 改用「分段输出 + CPU 规约」，无竞态 |
| 5 | `uint words[4] = uint[4](...)` 语法错 | GLSL 450 **不支持数组构造** | 用 `uvec4` 分量或分开变量 |
| 6 | `const uint*` 传参语法错 | GLSL **不支持 buffer 数组当指针传参** | 把取值逻辑内联进循环 |

**坑 3 特别值得记**：修之前测出"46 GFLOP/s"（看似快 17 倍），**是假的** —— 因为只算了 1/256 的工作量。

## 四、数值精度分析（为什么 split-K 的"误差"反而更小）

```
seq=1:
  朴素版    err_max = 3.01e-03
  split=2   err_max = 2.93e-03
  split=4   err_max = 2.13e-03
  split=8   err_max = 1.49e-03   ← ★ 最小
  split=16  err_max = 8.44e-04   ← 最小，但太慢

原因：split-K 把长累加链切成短链 ⇒ 浮点误差累积更少（数学上更优）

seq=8 报的"1/32768 不符"是【近零值的相对误差放大】：
  某个输出真值 ≈ 0，分子是 1e-7 级别的绝对误差 ⇒ 相对误差看起来大
  绝对误差仍在合理范围（err_max=5e-2 对总量级 1e2 而言是 5e-4 相对）
```

## 六、生产建议（写进引擎时用）

| 场景 | 内核 | split |
|---|---|---|
| **seq = 1（解码）** | `mm_bf16_splitk` | **8** |
| **seq 2~16（小批量）** | `mm_bf16_splitk` | **4** |
| **seq > 16（prefill）** | `mm_bf16_splitk` 或朴素版 | 2 |

**注意**：split-K 需要额外 `split × n_out × seq × 4` 字节的临时缓冲
（seq=1、split=8 时仅 128 KB），且需要 CPU 端规约（`split` 次加法/元素）。

## 七、下一步：接线到引擎（需要补的内核）

矩阵乘已经具备生产条件。要让 `tg_forward` 走 Vulkan，还需：

| # | 内核 | 复杂度 | 说明 |
|---|---|---|---|
| 1 | **RMSNorm** | 低 | 每个 token 归约，用 workgroup 内归约即可 |
| 2 | **RoPE** | 低 | 逐元素旋转，无依赖 |
| 3 | **Attention** | 中 | QK^T + softmax + PV 三步；seq 大时需分块 |
| 4 | **SiLU 激活** | 极低 | 逐元素 |
| 5 | **MoE 路由** | 中 | top-k + softmax（8 专家选 2）|
| 6 | **KV cache 管理** | 中 | GPU 侧环形缓冲 |
| 7 | **后端抽象层** | 中 | 统一 CUDA / Vulkan / CPU 接口 |

**预估**：内核 3~5 天，抽象层 1 天，接线与回归 1~2 天。
