# TGAI GO —— P1 / P2 实施方案（2026-10-10）

**背景**：用户要求做 P1（KV cache 量化 + 更激进量化）与 P2（CSA/GQA 混合层调度 + Attention Residuals）。
本文档给出**经过实测校准**的方案，并标注每项的难度与前置条件。

---

## 一、P1-A：转换器流式写盘 ✅ **已完成**

### 问题
原转换器把全部权重攒在 `weight_data` bytearray（V2.7 = 5.65 GB）⇒ 本机 15.4 GB 必 OOM。

### 解法（已实施）
两遍扫描：
```
第一遍：只算每个张量的输出字节数（不真正转换大张量）→ 定出布局
写占位：header + tokenizer + 权重表（offset 先写 0）+ padding
第二遍：逐张量转换 → 直接 f.write() → 记录 offset
回填  ：seek 回 header 改 weight_data_len；重写权重表的 offset
```

**峰值内存：5.65 GB → 约 300 MB**（单个最大张量 128 MB + 元信息）。

### 验证（TGAI MINI，61 MB 模型）
产物与官方 `TGAI MINI V1 15e.TG` **同尺寸 3,142,704 B**，header 逐字段比对：

| 字段 | 流式产物 | 官方产物 | 判定 |
|---|---|---|---|
| n_layers / d_model / n_heads / d_ff | 6/192/6/768 | 6/192/6/768 | ✅ 同 |
| vocab_size / max_seq_len | 8192/128 | 8192/128 | ✅ 同 |
| tokenizer_off / len | 128/55128 | 128/55128 | ✅ 同 |
| weight_table_off / count | 55256/80 | 55256/80 | ✅ 同 |
| **weight_data_off** | **59424** | **59424** | ✅ **同** |
| **weight_data_len** | **3083280** | **3083280** | ✅ **同** |
| version | 3（v3）| 1（v1）| 格式演进 |
| modality_flags | 0x1（TEXT）| 0x0 | 格式演进 |
| **pad/bos/eos/unk** | **0/2/3/1** | 0/1/2/3 | ★ **官方是错的** |

**★ 顺带修正了一个历史 bug**：
`tokenizer_hf.json` 的权威映射是 `<PAD>=0 <UNK>=1 <BOS>=2 <EOS>=3`，
而官方产物写的是 `0/1/2/3`（把 UNK 和 BOS/EOS 搞反了）。新转换器按 added_tokens 取，**正确**。

### 运行时验证
```
流式产物: ✅ 加载成功  layers=6 d_model=192 vocab=8192 max_seq=128
          encode("hello") = [2, 7373, 3]   forward ✅
官方产物: ✅ 加载成功（需纯 ASCII 路径 —— 引擎用窄字符 API，中文路径会报"无法打开文件"）
```

## 二、P1-B：更激进的量化（Q4_0 → Q3_K / Q2_K）

### 为什么这是 B 的正确解法（实测支撑）

```
每 token 需读 MoE 权重 = 206.7 MB
实测有效带宽        = 3.03 GB/s（4 线程可用 8.60 GB/s ⇒ 只发挥 35%）
单核读带宽          = 2.54 GB/s ⇒ 内存【延迟】受限
```

**⇒ 既然是带宽/延迟受限，减少字节数就是最直接的提速。**

| 格式 | bit/权重 | 相对 Q4_0 | 预期提速 | 质量 |
|---|---|---|---|---|
| Q4_0 | 4.5 | 1.00 | 1.00x | 基线 |
| **Q4_K** | 4.5 | 1.00 | ~1.0x | **更好**（分块 scale+min 两级）|
| **Q3_K** | 3.4 | **0.76** | **~1.3x** | 略降 |
| **Q2_K** | 2.6 | **0.58** | **~1.7x** | 明显降 |

### 实施要点（llama.cpp 的 K-quant 结构）

Q4_K 的 super-block（256 权重 = 144 字节）：
```
2B  fp16 d   (super-block scale)
2B  fp16 dmin(super-block min)
12B 6-bit 的 8 个子块 scale
12B 6-bit 的 8 个子块 min
128B 4-bit 量化值
```
**复杂度明显高于 Q4_0 的 18 字节/32 权重**，需要：
1. 转换器侧的量化实现（含 6-bit 打包）
2. 引擎侧的反量化 + 点积内核（AVX2 路径）

**⚠️ 工作量评估：3~5 天**（量化器 + 内核 + 逐位验证 + 质量对比）

### 更务实的中间步骤（建议先做）
**Q5_0 / Q4_1**（都是 32 权重一组的简单块格式，与 Q4_0 同族）：
| 格式 | 字节/32权重 | 相对 Q4_0 | 说明 |
|---|---|---|---|
| Q4_0 | 18 | 1.00 | 有 |
| **Q4_1** | 20 | 1.11 | 加 min 偏移，**质量更好** |
| Q5_0 | 22 | 1.22 | 5-bit |
| **Q5_1** | 24 | 1.33 | |

**⇒ 这些实现量只有 Q4_0 的 1.2 倍，1 天可完成一个。**

## 三、P2-A：CSA / GQA 混合注意力层调度

### V3 的设计（计划书原文）
```
每 4 层调度如下：
  3 层 压缩稀疏 CSA（Compressed Sparse Attention）
  1 层 全局 GQA
  KV 低秩压缩（MLA 式）
```

### 实施要点

**① 层类型表**（在 .TG header 或配置里加）
```c
/* 新增：每层的注意力类型 */
#define TG_ATTN_GQA_GLOBAL   0   /* 全局 GQA（现有实现）*/
#define TG_ATTN_CSA          1   /* 压缩稀疏 */
/* header 扩展：用 extension_off 指向一个 layer_types[] 数组 */
```

**② CSA 的核心机制**（参考 DeepSeek-V4 的 CSA/HCA 思想）
```
输入 x [seq, d]
  ↓ 压缩：把每 K 个 token 压成一个"块表示"（低秩投影）
  ↓ 稀疏：只对 query 相关的 Top-N 块做注意力
  ↓ 输出 [seq, d]
收益：长上下文下 attention 的 FLOPs 从 O(seq²) 降到 O(seq·N)
```

**③ KV cache 布局变化**
- GQA 层：常规 KV cache
- CSA 层：**压缩后的块表示**（尺寸 = seq/K），KV 内存大幅降低

### ⚠️ 难点与前置条件

| 难点 | 说明 |
|---|---|
| **需要新 kernel** | 压缩 + 稀疏选择在 DCU 上无现成算子（V3 计划书 §十一风险 1 也提到）|
| **需要 V3 模型才有意义** | V2.7 是标准注意力，改引擎无法验证 |
| **需要 .TG 格式扩展** | layer_types 数组 + 压缩矩阵的权重命名 |

**⇒ 建议：等 V3 的 `model_v3.py` 定型后再做。现在可以先做「层类型分派框架」（不含 CSA 实现）**，
让引擎能按层类型走不同路径 —— 这样 V3 一来就能接。

### 可立即做的部分（1~2 天）
```c
/* tgai_engine.c 的 transformer_block 里加分派 */
switch (m->layer_type[i]) {
    case TG_ATTN_GQA_GLOBAL:  attn_gqa(...);  break;   /* 现有实现 */
    case TG_ATTN_CSA:         attn_csa(...);  break;   /* 预留桩，返回错误 */
    case TG_ATTN_DENSE:       attn_dense(...); break;
}
```
配合 `.TG` 格式的 `layer_types` 扩展（用 `extension_off`，向后兼容）。

## 四、P2-B：Attention Residuals（AttnRes）

### V3 的设计（计划书原文）
> **Attention Residuals**（Kimi-K3 的 AttnRes）：每块可选择性援引前层表示，
> 跨层直连通路，加强深层信息流。V3 采用简化版：**每 4 层做一次残差特征门控聚合**。

### 机制
```
普通残差：  x = x + Block(x)
AttnRes：   x = x + Block(x) + gate(x) ⊙ Pool(前几层的表示)

其中 gate 是一个小的可学习门控（或按相似度计算），
Pool 可以是「前 4 层表示的加权和」。
```

### 实施要点
| 项 | 内容 |
|---|---|
| **新增权重** | 门控参数（每 4 层一组）⇒ .TG 权重命名如 `blocks.{i}.attnres.gate.weight` |
| **新增 buffer** | 保存前几层的表示（`work_attnres[4][seq][d]`）⇒ 内存增加 4×seq×d |
| **前向改动** | 在每 4 层的边界做门控聚合 |
| **向后兼容** | 无 `attnres` 权重 ⇒ 跳过（判定 NULL）|

**⇒ 工作量 2~3 天，且同样需要 V3 模型验证。**

### 可立即做的部分
1. `.TG` 权重名规范里预留 `blocks.{i}.attnres.{gate,pool}.weight`
2. 引擎加载时探测（存在则启用，缺失则跳过）
3. 前向实现 + 用**合成权重**做数值验证（不需要真模型）

| # | 任务 | 状态 | 前置条件 | 工作量 |

### ★ 关键判断
**P2 的两项（CSA / AttnRes）都需要 V3 模型才能验证。**
现在能做的是「**框架先行**」：把 `.TG` 格式扩展、层类型分派、权重探测做好，
等 V3 的小规模验证模型（计划书 P1 阶段的 100M 模型）一出来就能直接接上。

**这符合 V3 计划书 §十一风险 3 的策略**：
> 资源到位前，所有 P0–P1 资产（词表/数据/代码/验证日志）先行沉淀。
